# BitsScore 评估工作流（前期准备、代码安全、链上）

这份工作流是给**执行评估的 agent** 用的。它把「给项目打分」拆成一张张步骤卡，每张卡都写清五件事：

1. 这一步在做什么；
2. 去哪里拿数据、怎么拿；
3. 怎么判断，从固定选项里选；
4. 往哪个文件的哪个字段填；
5. 怎么检查自己做完了。

**你只负责填事实。** 定档、算分、出结果都由脚本完成，你不需要也不应该自己算分。规则的来源是[评分骨架](../评分骨架.md)、[代码安全评分标准](../code-security/code-security-rating-standard.md)和[链上安全评估标准](../onchain/链上安全评估标准.md)，具体计算写在 [scripts/bitsscore.py](./scripts/bitsscore.py) 和 [scripts/onchain.py](./scripts/onchain.py) 里。

## 开始

```bash
python3 工作流/scripts/bitsscore.py init 评估记录/<项目>/<评估ID>
```

这条命令会在 `评估记录/<项目>/<评估ID>/` 下生成全部空白模板。模板里所有要填的地方都写着 `__填写__: 说明`。把整串 `__填写__: …` 替换成你的答案即可，不要保留 `__填写__` 前缀。

**目录约定。** 每个项目一个目录，每次评估一个子目录，子目录名就是评估 ID（`<项目>-<年月日>`）。重评时新建子目录，旧目录不再修改。在项目目录上运行 `history`，生成这个项目所有评估的索引 `index.md`：

```bash
python3 工作流/scripts/bitsscore.py history 评估记录/<项目>
```

## 步骤总表

按顺序做，**上一步的检查不通过，不要开始下一步**。

| 步骤 | 步骤卡 | 你要做什么 | 产出文件 | 做完后运行 |
| --- | --- | --- | --- | --- |
| T0 | [任务单](./步骤卡/T0-任务单.md) | 记下评什么项目、哪些链、范围 | `T0-task.json` | `validate <目录> --step T0` |
| P1 | [锁定生产部署](./步骤卡/P1-锁定生产部署.md) | 找到用户实际调用的入口和实际执行的代码 | `P1-baseline.json` | `validate <目录> --step P1` |
| P2 | [核验源码](./步骤卡/P2-核验源码.md) | 拿到与链上一致的源码，检出到本地 | `P2-sources.json` | `validate <目录> --step P2` |
| P3 | [业务与模块](./步骤卡/P3-业务与模块.md) | 列出业务功能和每个源码模块 | `P3-business-modules.json` | `validate <目录> --step P3` |
| P4 | [职责与档位](./步骤卡/P4-职责与档位.md) | 把代码切成职责，回答两个是非题 | `P4-responsibilities.json` | `validate <目录> --step P4`，然后运行 `lines <目录>` |
| P5 | [角色与控制](./步骤卡/P5-角色与控制.md) | 找出所有特权角色和特权操作 | `P5-roles-controls.json` | `validate <目录> --step P5` |
| P6 | [前期准备交付](./步骤卡/P6-前期准备交付.md) | 生成关系图，做交付前复核 | `P6-graph.md` | `graph <目录>` |
| C1 | [有效行统计](./步骤卡/C1-有效行统计.md) | 运行脚本，处理报警 | `C1-lines.json`（脚本生成） | `lines <目录>` |
| C2 | [登记审计报告](./步骤卡/C2-登记审计报告.md) | 找全报告，登记受审版本和范围 | `C2-reports.json` | `validate <目录> --step C2` |
| C3 | [判定覆盖](./步骤卡/C3-判定覆盖.md) | 运行脚本，对每处代码改动回答「行为有没有变」 | `C3-semantic-changes.json`、`C3-coverage.json` | `coverage <目录>` |
| C4 | [登记发现](./步骤卡/C4-登记发现.md) | 登记每条发现的等级、是否仍存在、修复状态 | `C4-findings.json` | `validate <目录> --step C4` |
| C5 | [总体评价](./步骤卡/C5-总体评价.md) | 回答找补和扣分的是非题，记录反常写法线索（由人确认） | `C5-overall.json` | `validate <目录> --step C5` |
| C6 | [计分与交付](./步骤卡/C6-计分与交付.md) | 运行脚本，交付结果 | `C6-score.json`、`C6-score.md` | `score <目录>` |
| O1 | [范围与快照](./步骤卡/O1-范围与快照.md) | 定快照，复核基线，列业务、必要操作和市场，登记模块对应的顶层链上对象 | `O1-scope.json` | `validate <目录> --step O1` |
| O2 | [读取清单](./步骤卡/O2-读取清单.md) | 列出要读的对象和字段，不超预算 | `O2-targets.json` | `validate <目录> --step O2` |
| O3 | [读数回填](./步骤卡/O3-读数回填.md) | 在快照上读出每个字段，原样照抄 | `O3-readings.json` | `validate <目录> --step O3` |
| O4 | [角色关系与权限路径](./步骤卡/O4-权限路径.md) | 在关系图上补齐角色的链上持有人（多签、时间锁、签名地址），登记 H1／H2／H3 路径 | `O4-permissions.json`、`O4-role-graph.md` | `validate <目录> --step O4`，然后 `role-graph <目录>` |
| O5 | [参数配置](./步骤卡/O5-参数配置.md) | 逐行过专项第 3 节：填公式输入或回答是非题 | `O5-config.json` | `validate <目录> --step O5` |
| O6 | [资金与依赖](./步骤卡/O6-资金与依赖.md) | 逐行过专项第 4 节和预言机检查 | `O6-funds.json` | `validate <目录> --step O6` |
| O7 | [致命项](./步骤卡/O7-致命项.md) | 登记致命项候选（由人确认） | `O7-fatal.json` | `validate <目录> --step O7` |
| O8 | [TVL 与计分](./步骤卡/O8-TVL与计分.md) | 填 TVL，运行脚本，交付结果 | `O8-tvl.json`、`O8-score.json`、`O8-score.md` | `onchain-score <目录>` |

表中的命令都要加上前缀 `python3 工作流/scripts/bitsscore.py`。

**最后一步：生成交付 JSON。** 所有要评的维度做完后运行 `export <目录>`，生成 `deliverable.json`。这是前端唯一的数据源，格式见[交付格式](./交付格式.md)。

- 只做代码安全：T0–P6，然后 C1–C6。
- 只做链上：T0–P6，然后 O1–O8。
- 两个都做：T0–P6 之后，C 和 O 两条线互不依赖，可以分开做。

每个交付物有哪些字段、取值和约束，见[交付物字段表](./交付物字段表.md)（由脚本从字段定义生成）。

## 人工复核中间产物

规则还在对齐阶段，每一步的产出都要由人看过。agent 做完一步、检查通过后，交给人复核；人用下面的命令记录结论：

```bash
python3 工作流/scripts/bitsscore.py review 评估记录/<项目>/<评估ID> O4 --reviewer 张三 --verdict pass
python3 工作流/scripts/bitsscore.py review 评估记录/<项目>/<评估ID> O5 --reviewer 张三 --verdict needs_fix --comment "CK04 的单位换算不对"
python3 工作流/scripts/bitsscore.py review-status 评估记录/<项目>/<评估ID>
```

- 复核结果存在评估目录的 `reviews.json`，记录了当时每个文件的指纹。文件之后被改过，这条复核会自动显示「已过期」，需要重新复核。
- `needs_fix` 的意见由 agent 修改后，人再复核一次。
- **agent 不写 `reviews.json`。**
- 复核不影响计分，只记录对齐过程。B1 和致命项的「人工确认」是计分规则的一部分，照旧在 C5、O7 里填。

## 必须遵守的规则

1. **不要猜。** 查不到、看不懂、拿不准的，不要编一个答案。在 `gaps.json` 里登记一条缺口（写清缺什么、查过哪里），然后继续做能做的部分。
2. **只填选项里有的值。** 字段要求 `yes | no`，就只能填 `yes` 或 `no`。
3. **每个事实都要有证据。** 证据是链接、交易哈希、源码位置（`路径:起始行-结束行`）或命令。「我认为」不算证据。
4. **不要手改脚本生成的文件。** 包括 `C1-lines.json`、`C3-coverage.json`、`C6-*`、`O8-score.*`、`deliverable.json`、`P6-graph.md`、`O4-role-graph.md`，以及 `C3-semantic-changes.json` 里标着「脚本生成」的字段。
5. **不要自己算分，也不要改脚本。** 觉得脚本的结果不对，就把情况写进报告，交给人处理。
6. **每一步做完都运行检查命令。** 检查会列出所有问题，按提示逐条改，直到显示「检查通过」。

## 填写格式约定

| 内容 | 格式 | 例子 |
| --- | --- | --- |
| 链 | `sui:mainnet` 或 `evm:<chainId>` | `evm:1`、`evm:42161` |
| 地址 | 小写。Sui 写完整的 `0x` 加 64 位（短地址补零）；EVM 写 `0x` 加 40 位 | `0x0000…0002` |
| 证据 | 只能是五种格式之一：网址 `https://…`；交易 `tx:<链>:<哈希>`；命令 `cmd:<完整命令>`；本地文件 `file:<路径>`；源码位置 `<路径>:<起>-<止>` | `tx:sui:mainnet:8hX…`、`cmd:cast call 0x… "owner()" --block 21000000` |
| ID | 固定前缀加两位以上数字 | `B01` `I01` `S01` `BZ01` `M01` `D01` `R01` `K01` `G01` `AR01`；链上：`MK01` 市场、`OT01` 读取目标、`RD01` 读数、`PR01` 控制者、`PA01` 路径、`CK01` 检查、`XF01` 致命项候选 |
| 源码位置 | `相对路径:起始行-结束行` | `sources/lending.move:120-168` |
| 日期 | `YYYY-MM-DD` | `2026-11-25` |
| 时间 | ISO8601，UTC，以 `Z` 结尾 | `2026-11-25T08:00:00Z` |
| commit | 完整 40 位小写十六进制 | `9ff791fe309358a8bf6f3783a2aeb0c95f72a1dd` |

## 每张步骤卡的结构

每张卡都按同样的顺序写：**这一步在做什么 → 开始前你需要 → 产出 → 操作步骤 → 怎么判断 → 填写示例 → 完成检查 → 常见错误 → 卡住了怎么办**。

## 链上数据

工作流只规定**读什么**（O2 读取清单）和**读到的值长什么样**（O3 读数），不规定用什么工具去读。手工调用节点、用采集工具或脚本、看区块浏览器都可以，只要读数满足 O3 的格式，并且能用 `evidence` 复现。采集工具是独立的东西，工作流不依赖它的内部格式。

链上计分只用**单次快照**能直接读到的数据。需要扫描历史交易、枚举全部用户才能得到的数，只披露，不计分。参数没有查询函数时怎么读、什么时候允许定向读一笔交易，见 [O3 卡](./步骤卡/O3-读数回填.md#拿不到数据时按这个顺序试)。
