# 交付 JSON 格式（schemaVersion 3.0）

`deliverable.json` 是一次评估的**最终交付物**，也是前端展示的**唯一数据源**。

- 只由 `python3 工作流/scripts/bitsscore.py export <目录>` 生成，不手写、不手改。
- 机器可读的格式定义：[scripts/deliverable.schema.json](./scripts/deliverable.schema.json)（JSON Schema 2020-12）。前端可以直接用它做校验。
- `export` 写出前会做三项自检，任何一项不通过都不写出文件：
  1. 符合 Schema；
  2. 所有证据引用都能在证据字典里找到；
  3. **树上每个节点的分数都能按它写明的规则，从子节点复算出来。**

## 1. 核心结构：一棵证据树

```text
根（项目，不出总分）
├ 代码安全（维度分）
│ ├ 审计覆盖 → 档 → 职责 → 源码区间（叶子：覆盖状态、覆盖它的报告）
│ ├ 总体评价 → 加减分项（叶子：事实）
│ └ 风险封顶 → 发现（叶子：报告、等级、修复状态）
├ 链上安全（维度分）
│ └ 业务
│   ├ 权限管理 → H1／H2／H3 → 路径 → 控制者 → 多签成员（叶子：地址、读数）
│   ├ 参数配置 → 市场 → 检查项 → 读数或常量（叶子）
│   ├ 资金与外部依赖 → 市场 → 检查项 → 读数或常量（叶子）
│   └ 致命项（叶子：事实）
├ 业务攻防（本轮未评估）
└ 盘外情报（本轮未评估）
```

- **叶子**是原始事实：链上读数、代码常量、源码区间、报告发现、人工确认的事实。
- **中间节点**是判断：每个节点都写明自己的分数是怎么从子节点得来的（`rule`）。
- **维度节点**是维度分。
- **根节点不出总分**。骨架没有定义跨维度的合成规则，这里不另行编造。

所有节点都是同一种结构，前端用一个递归组件就能逐层展开。

## 2. 节点结构

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | 字符串 | 节点路径，全树唯一，例如 `onchain/BZ01/configuration/MK01/L-C2.1` |
| `kind` | 枚举 | 节点类型，见第 3 节 |
| `label` | 字符串 | 显示名 |
| `status` | 枚举或 `null` | 见第 4 节。只有根节点为 `null` |
| `score` | 数字或 `null` | 只有 `status` 为 `rated` 时才有值，保留两位小数 |
| `weight` | 数字或 `null` | 本节点在父节点加权平均里的权重（0–1）；父节点不是加权平均时为 `null` |
| `rule` | 对象 | `method`：本节点的分数怎么从子节点得来，见第 5 节；`text`：给人看的说明，带实际数字 |
| `summary` | 字符串或 `null` | 维度节点的一句话摘要，由固定模板生成 |
| `refId` | 字符串或 `null` | 对应工作流里的原始 ID（例如 `RD01`、`PA01`、`CK03`）。同一个叶子出现在多处时，`refId` 相同 |
| `data` | 对象 | 这类节点特有的数据，见第 3 节 |
| `evidenceIds` | 数组 | 指向顶层 `evidence` 字典 |
| `children` | 数组 | 子节点 |

**同一个叶子被多处引用时**（例如一条价格读数被几个检查用到，一个多签同时控制几条路径），每个用到它的位置都放一份完整的节点，前端展开哪一支都能直接看到内容。这些副本的 `id` 不同，`refId` 相同。

## 3. 节点类型

| `kind` | 层级 | `data` 中的主要字段 |
| --- | --- | --- |
| `root` | 根 | — |
| `dimension` | 维度 | 代码安全：`blockers`、`ruleVersion`。链上：`weighting`（tvl／equal）、`budget`、`dimensionView`、`blockingGapIds`、`ruleVersion` |
| `coverage` | 代码：审计覆盖（0–90） | `max` |
| `tier` | 代码：档 | `tier`（5／3／1）、`lines`、`covered`、`coveredDirect`、`coveredCarried`、`uncoveredByReason` |
| `responsibility` | 代码：职责 | `lines`、`covered`、`q1`、`q2` |
| `code_range` | 代码：源码区间（叶子） | `sourceId`、`file`、`start`、`end`、`effectiveLines`、`coverage`、`uncoveredReason`、`reportIds` |
| `overall` | 代码：总体评价（0–10） | `max` |
| `adjustment` | 代码：加减分项（叶子） | `code`、`points`、`fact` |
| `observation` | 代码：B1 反常写法线索（叶子） | `signal`、`location`、`description` |
| `cap` | 代码：风险封顶 | — |
| `finding` | 代码：报告发现（叶子） | `reportId`、`findingId`、`severity`、`fixStatus`、`capping` |
| `business` | 链上：业务 | `specialty`、`specialtyVersion`、`tvlUsd`、`notes`、`incompleteReasons`、`zeroMarkets`、`marketCoverage`（只选了部分市场时：`selectedTvlUsd`、`businessTvlUsd`、`ratio`、`sameSource`（两个 TVL 是否同一口径）；没有市场时为 null） |
| `aspect` | 链上：三个大项 | 权限大项另有 `keyConcentration`（密钥集中度，只披露）：`pathsConsidered`；`allPathsKeys`（走通全部路径最少要几把密钥）；`levels[]`（每一层的 `keys`、`addresses`、`memberOf`（地址所在的多签及门限）、`controlledPaths`、`uncontrolledPaths`）；有 H3 发起者时另有 `temporaryBlock`（临时阻断，只披露）：`minKeys`（最少几把密钥就能发起阻断）、`pathIds` |
| `consequence` | 链上：H1／H2／H3 | — |
| `path` | 链上：权限路径 | `description`、`declaredConsequence`、`minKeys`、`effectiveDelaySeconds`、`delaySeconds`、`delayPublic`、`delayBypass`、`exitClosableInDelay`、`note`、`initiatorIds`（H3 的发起者）、`initiatorMinKeys`（发起阻断最少几把密钥） |
| `controller` | 链上：控制者 | `kind`（eoa／multisig／other）、`address`、`chainId`、`threshold`、`memberWeight` |
| `absent` | 链上：确认不存在某类后果（叶子） | `verified` |
| `market` | 链上：市场 | `object`、`tvlUsd`、`discoveredBy` |
| `check` | 链上：检查项 | `checkId`、`marketId`、`reason` |
| `reading` | 链上：读数（叶子） | `object`、`field`、`value`（原样字符串）、`unit`、`method`、`methodDetail`、`atSnapshot`、`chainId`；作为公式输入时另有 `input`、`divideBy`、`note` |
| `constant` | 链上：公式常量（叶子） | `input`、`value` |
| `fatal` | 链上：致命项（叶子） | `kind`（X1–X3）、`decision`、`fact` |

## 4. 状态

| `status` | 意思 | 前端建议 |
| --- | --- | --- |
| `rated` | 已出分 | 显示分数 |
| `incomplete` | 评估未完成：必需的事实没读到 | 不显示分数；维度和业务节点的 `data` 里有原因 |
| `pending_review` | 待人工确认 | 不显示分数，标「待确认」 |
| `not_applicable` | 机制不存在 | 显示 N/A |
| `not_assessed` | 本轮没评 | 显示「未评估」 |
| `reference` | 引用别的检查，这里不计分 | 显示「参见…」 |
| `disclosure` | 只披露，不计分 | 显示读数，不显示分数 |
| `excluded` | 权限路径不构成该后果（例如会自动到期的暂停） | 灰显 |
| `info` | 叶子事实，本身不计分 | 显示内容 |

## 5. 聚合规则（`rule.method`）

| `method` | 意思 | 自检怎么复算 |
| --- | --- | --- |
| `min` | 取子节点中的最低分 | 子节点里 `rated` 的最低分 |
| `weighted_mean` | 按子节点的 `weight` 加权平均 | 只用 `rated` 的子节点，权重重新归一。审计覆盖节点再乘以 0.9（满分 90） |
| `cap` | 封顶。代码安全维度：min(覆盖分 + 总体评价, 封顶) | 按公式复算 |
| `sum` | 累加（总体评价：5 + 加分 − 扣分，限制在 0–10） | 不复算，看子节点逐项核对 |
| `lookup` | 查表（权限路径：最少密钥数 × 有效延时） | 不复算，`rule.text` 写明查表输入和结果 |
| `formula` | 公式（检查项） | 不复算，`rule.text` 写出计算过程 |
| `answer` | 由是非题定档（检查项） | 不复算，`rule.text` 写明落在哪一档 |
| `override` | 被覆盖（确认的致命项使业务分记 0） | 分数必须为 0 |
| `none` | 叶子，或不计分的节点 | — |

## 6. 顶层字段

| 字段 | 说明 |
| --- | --- |
| `schemaVersion` | `"3.0"` |
| `assessmentId` | 评估 ID，格式 `<项目>-<年月日>`，同一天第二次加 `-2` |
| `history` | `previousAssessmentId`（上一次评估的 ID，首次为 `null`）、`reason`（first／scheduled／permission_change／upgrade／parameter_change／rule_change／correction）。前端可以顺着 `previousAssessmentId` 找到同一项目的历次结果 |
| `generatedAt` | 生成时间（UTC） |
| `project` | `name`、`chains[]`（`chainId`、`name`） |
| `ruleVersions` | `skeleton`、`codeSecurity`、`onchain`、`workflow`、`specialties`。没评的维度为 `null` |
| `snapshots` | 快照列表，每项带 `dimension`（`code_security`：部署基线，代码安全评估的是这个时点实际执行的代码；`onchain`：链上快照，权限、参数、资金都按这个时点读取）、`purpose`、`chainId`、`blockOrCheckpoint`、`hash`、`timeUtc`。两个维度的时点可以不同，**各自的分数只代表各自的时点** |
| `validity` | `invalidatedBy`：发生哪些事件后结果过期 |
| `tree` | 证据树的根节点 |
| `roleGraph` | 链上角色关系图（只评代码安全时为 `null`），见第 6.1 节 |
| `reports` | 审计报告：`id`、`firm`、`type`、`date`、`url` |
| `gaps` | 证据缺口：`id`、`step`、`missing`、`blocking` |
| `evidence` | 证据字典：键为 `EV-` 加 10 位十六进制，值为 `kind`（url／tx／command／file／code）、`ref`（原始引用）、`url`（能生成链接的给出链接，否则 `null`） |

### 6.1 `roleGraph`：链上角色关系图

证据树回答「分数怎么来的」，关系图回答「谁控制什么」。它是前期准备关系图的延伸：在模块—角色—控制的基础上，补上链上实体。

- `nodes[]`：`id`、`kind`、`label`，以及各类节点的附加字段。`kind` 取值：
  - 前期准备阶段：`business`、`module`、`role`、`control`（附 `consequence`）；
  - 链上阶段：`object`（模块对应的顶层链上对象，附 `objectKind`、`chainId`）、`eoa`、`multisig`（附 `threshold`）、`timelock`（附 `delaySeconds`）、`other`、`no_holder`（凭证已销毁或查不到持有人）。
- `edges[]`：`from`、`to`、`kind`。`kind` 取值：
  - 前期准备阶段：`uses`（业务使用模块）、`calls`（模块调用模块）、`grants`（角色授予角色）、`can_call`（角色可调用控制）、`affects`（控制作用于模块）；
  - 链上阶段：`deployed_as`（模块对应链上对象）、`held_by`（角色由谁持有，附 `credential`）、`signer`（多签的签名人，附 `weight`）、`proposer`（时间锁的提议者）。
- **同一个链上实体只有一个节点。** 两个角色由同一个多签持有，这个多签节点同时连到两个角色；两个多签有共同签名地址，这个地址同时连到两个多签。
- 证据树里的 `controller` 节点，`refId` 就是关系图里对应节点的 `id`（例如 `PR05`），两边可以互相跳转。

## 7. 全局约束

| 约束 | 规则 |
| --- | --- |
| 分数 | 0–100 的数字（审计覆盖 0–90、总体评价 0–10）或 `null`，保留两位小数。不出现字符串分数、分数式精确值或上下界 |
| 时间 | UTC，ISO8601，以 `Z` 结尾 |
| 链 | `sui:mainnet`、`evm:<chainId>` |
| 证据 | 节点里只放 `evidenceIds`，链接统一放在 `evidence` 字典 |
| 文案 | 只放评估数据和固定模板生成的说明。图标、按钮、卡片标题、英文标签由前端维护 |
| 维度 | 根节点下固定 4 个维度节点，顺序固定：代码安全、链上、业务攻防、盘外情报 |
| 历史版本 | 不内嵌。重评在新目录生成新的文件，旧目录原样保留；项目目录下的 `index.json` 由 `history` 命令生成，列出历次评估 |

## 8. 和旧格式（Cetus、NAVI 试评）的对应

| 旧格式 | 新格式 |
| --- | --- |
| `dimensions[]` 平铺，`breakdownKey` 再指向各自的明细对象 | 根节点下的 4 个维度节点，明细就是它们的子树 |
| `dimensions[].id`：`code`／`onchain`／`business`／`other` | 维度节点 `id`：`code_security`／`onchain`／`business_security`／`intelligence` |
| 自造状态：`rated_verified_lower_bound`、`project_coverage_estimate`、`reported_by_module`、`trial_rating` 等 | 第 4 节的固定枚举 |
| `score`、`scoreExact`、`lower`／`upper`、`pendingShare` | 只有 `score`。缺事实就是 `incomplete`，不做推断区间 |
| `onchainAssessment` 下 25 个并列字段 | 链上维度节点的子树，一个事实只挂在它支撑的判断下面 |
| `moduleRatings.*.subchecks`、`criteria` 等层级不一的明细 | 统一的节点结构，层级由 `kind` 表明 |
| 分数和结果写成字符串（`"80"`、`"N/A"`） | 数字或 `null`，另用 `status` 表达 |
| `evidence` 字典（字段不统一）、`evidenceRefs` 指向 JSON 路径 | `evidence` 字典固定字段；节点用 `evidenceIds` 引用 |
| `reportLibrary.reports` | `reports` |
| `supersededAssessments` | 不内嵌 |
| `profile` 里的展示文件（卡片、导航、说明文字） | 不属于交付 JSON，前端从树生成 |

- 新增可选的 `data` 字段、不影响前端现有读取：`schemaVersion` 不变，在本文件第 3 节补充。
- 改名、删字段、改类型或枚举、改树的层级：升级 `schemaVersion`，并在下表记录。

| 日期 | 版本 | 内容 |

| 2026-11-25 | 3.0 | 改为统一节点的证据树：叶子是原始事实，中间节点写明聚合规则，导出时逐层复算 |
