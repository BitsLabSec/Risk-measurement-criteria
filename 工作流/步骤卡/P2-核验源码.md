# P2 核验源码

## 这一步在做什么

找到与 P1 实际执行代码**一致**的源码，检出到本地，并留下「两者一致」的证据。后面数行数、比对审计版本，都只用这份源码。

## 开始前你需要

- `P1-baseline.json` 已通过检查
- 能运行 `git`；如果项目在 Sui 上，最好装好 `sui` CLI

## 产出

`P2-sources.json`：每个**不同的实现版本**一条记录。多个部署实例用的是同一份实现时，合成一条，`deployment_ids` 列出全部实例。

## 操作步骤

1. **找候选源码。** 按优先级依次尝试：
   1. 区块浏览器上已验证的源码（Etherscan 的 "Contract Source Code Verified"；Sui 浏览器的 Code 页）；
   2. Sourcify（EVM）；
   3. 项目的 GitHub 仓库：找与部署时间最接近的 tag 或 release。Sui 项目还要看 `Move.toml` 里的 `published-at`，它要等于 P1 的包 ID。
2. **检出到本地，固定 commit：**
   ```bash
   git clone <仓库URL> <本地目录>
   git -C <本地目录> checkout <commit>
   git -C <本地目录> rev-parse HEAD     # 输出就是要填的 40 位 commit
   ```
3. **核验一致性**，按下表选一种方法。
4. **划定统计范围。**
   - `in_scope_globs`：项目自己写的合约源码，例如 `sources/**/*.move` 或 `contracts/**/*.sol`。
   - `excluded_globs`：第三方库、测试、脚本、mock，例如 `**/tests/**`、`lib/**`、`node_modules/**`、`**/mock*`。

## 怎么判断（核验方法）

| `verify_method` | 怎么做 | 什么情况下 `verify_result` 填 `match` |
| --- | --- | --- |
| `explorer_verified` | 浏览器显示已验证，并且你下载的源码和本地 commit 的文件内容一致 | 逐个比对范围内的文件，内容都相同 |
| `sui_verify_source` | 在本地源码目录运行 `sui client verify-source --verify-deps`，并确认 `Move.toml` 的 `published-at` 是 P1 的包 ID | 命令输出验证成功 |
| `rebuild_and_compare` | 用相同版本的编译器重新编译，比对字节码（EVM 用 `eth_getCode` 读链上字节码） | 除元数据哈希外，字节码一致 |
| `sourcify_exact` / `sourcify_partial` | 在 Sourcify 查询该地址 | 返回 exact 或 partial match，且源码与本地 commit 一致 |
| `not_verified` | 以上方法都做不到 | 只能填 `not_verified` |

- 比对结果不一致时，`verify_result` 填 `mismatch`。
- **只要有一条不是 `match`，代码安全的结果就会变成「无法评分」。** 如实填写。

## 填写示例

```json
{
  "sources": [{
    "id": "S01",
    "deployment_ids": ["I01"],
    "language": "move",
    "repo_url": "https://github.com/naviprotocol/navi-smart-contracts",
    "commit": "9ff791fe309358a8bf6f3783a2aeb0c95f72a1dd",
    "local_path": "/work/navi-src",
    "in_scope_globs": ["lending_core/sources/**/*.move", "oracle/sources/**/*.move"],
    "excluded_globs": ["**/tests/**"],
    "verify_method": "sui_verify_source",
    "verify_result": "match",
    "verify_evidence": ["评估记录/navi-2026-11/证据/verify-source.txt"]
  }]
}
```

把命令输出保存成文件，放在评估目录的 `证据/` 下，然后在 `verify_evidence` 里写这个文件的路径。

## 完成检查

```bash
python3 工作流/scripts/bitsscore.py validate 评估记录/<评估ID> --step P2
```

检查会确认 `local_path` 目录存在、commit 格式正确，以及 P1 的每个部署实例都有对应的源码记录。

## 常见错误

- 直接用 `main` 分支，没有找到与部署对应的 commit。
- 把 OpenZeppelin、Sui framework 等第三方库也纳入了 `in_scope_globs`。
- 核验没有做成，却填了 `match`。

## 卡住了怎么办

找不到对应的源码，或者核验不一致时：`verify_result` 按实际情况填写，并在 `gaps.json` 登记缺口（`step` 填 `P2`，`blocks_denominator` 填 `true`）。然后继续用你能找到的最接近的源码完成 P3–P5，这样至少能交付已核实的部分。
