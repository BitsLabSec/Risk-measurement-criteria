# P4 职责与档位

## 这一步在做什么

把**每一行有效代码**归入一个「职责」，并对每个职责回答两个是非题。脚本根据你的答案自动给出核心（5）、重要（3）、辅助（1）的档位。档位决定这些代码在覆盖率中的权重。

## 开始前你需要

- `P3-business-modules.json` 已通过检查

## 产出

`P4-responsibilities.json`：每个职责一条。

## 什么是一个职责

一个职责 = 一个**能独立检查对错的结果**。例如：

- 「新增借款债务并从池中划款」
- 「计算健康因子」
- 「暂停开关」
- 「升级合约」
- 「事件和 getter」

要点：

- 一个职责可以跨多个函数、多个文件。把实现这个结果的所有源码区间都列进 `ranges`。
- 一个文件也可以拆成多个职责。

## 操作步骤

1. **从 P3 的每个用户入口出发**，顺着调用一路追下去，记下这条路径上产生的每一个结果，每个结果建一个职责。
2. **从每个特权函数出发**，同样建职责，例如「设置参数」「暂停」「升级」「提取协议费」。
3. **共享代码**（数学库、价格读取、权限检查）各建一个职责，供多个业务共用。
4. **兜底：** 最后建一个职责「其余代码」（例如 `D99`），`ranges` 覆盖所有范围内文件的全文，两个问题都答 `no`。
   - 行被多个职责覆盖时，脚本按最高档计。所以兜底职责只会接住那些没有被其他职责覆盖的行，例如 import、事件定义、getter。
   - **兜底不能代替第 1–3 步。** 脚本会把「看起来在操作资产、却被定成辅助档」的行报出来。
5. **对每个职责回答两个问题**，填写依据（见下表）。
6. 运行检查，再运行 `lines`，处理所有报警。

## 怎么判断

**问题 1（`q1_assets_or_authority`）**：这段代码是否**直接**做了下面任意一件事？

| 答 yes 的情况 | 例子 |
| --- | --- |
| 转移、铸造、销毁资产，或改变余额 | `balance::split`、`coin::take`、`transfer`、`_mint` |
| 改变用户的存款、债务、份额记录 | `user.debt = ...` |
| 计算价值，并且计算结果用于决定能借多少、能取多少、能否被清算 | 健康因子、价格换算、份额兑换率 |
| 检查或修改权限 | `assert!(sender == admin)`、授予或撤销 Cap |
| 升级合约，或者决定用哪份实现 | `package::authorize_upgrade`、`upgradeTo` |

**问题 2（`q2_preconditions_or_availability`）**：问题 1 答 no 时，这段代码是否影响**关键操作能不能执行、什么时候执行、在什么条件下执行**？

| 答 yes 的情况 | 例子 |
| --- | --- |
| 暂停、冻结、白名单开关 | `when_not_paused`、`set_pause` |
| 限额、上限、冷却时间的检查 | `assert!(amount <= cap)` |
| 版本检查 | `assert!(version == VERSION)` |
| 参数校验，校验不过就中止关键操作 | `assert!(ltv < threshold)` |

两个问题都答 no：事件、getter、只做展示的计算、常量定义等。

脚本的定档规则：问题 1 答 yes 是 5 档；否则问题 2 答 yes 是 3 档；否则是 1 档。

**依据怎么写**：写到具体行，例如 `lending.move:369 调用 pool::withdraw_balance_v2 划出资金`。答 no 的写 `无`。

## 填写示例

```json
{
  "id": "D01",
  "result": "新增借款债务并从池中划款",
  "business_ids": ["BZ01"],
  "module_ids": ["M02", "M03", "M04"],
  "ranges": [
    {"source_id": "S01", "file": "lending_core/sources/lending.move", "start": 352, "end": 380},
    {"source_id": "S01", "file": "lending_core/sources/logic.move", "start": 129, "end": 160},
    {"source_id": "S01", "file": "lending_core/sources/pool.move", "start": 216, "end": 232}
  ],
  "q1_assets_or_authority": "yes",
  "q1_evidence": "调用 pool::withdraw_balance_v2 划出资金；增加用户债务",
  "q1_locations": ["lending_core/sources/lending.move:369-369", "lending_core/sources/logic.move:140-140"],
  "q2_preconditions_or_availability": "yes",
  "q2_evidence": "借款前检查暂停开关",
  "q2_locations": ["lending_core/sources/lending.move:363-363"],
  "impact_object": "各资产池余额、用户债务",
  "failure_consequence": "可能多借、少记债或从错误的池划款"
}
```

## 完成检查

```bash
python3 工作流/scripts/bitsscore.py validate 评估记录/<项目>/<评估ID> --step P4
python3 工作流/scripts/bitsscore.py lines 评估记录/<项目>/<评估ID>
```

`lines` 必须满足两条：

- **未归档 0 行**；
- **没有「疑似定档过低」的报警**。如果有报警，逐行复核问题 1。复核后确认确实不是资产操作（例如只是在注释性的 getter 里出现了 `transfer` 这个词），就在 `gaps.json` 里写一条说明（`step` 填 `P4`，`blocks_denominator` 填 `false`），写清这些行为什么不是资产操作。

## 常见错误

- 整个文件只建一个职责，问题 1 一律答 no。这样核心代码会被当成辅助代码，分数就失真了。
- 行号对的是 `main` 分支，而不是 P2 检出的 commit。
- 答了 yes，依据却写得很空，例如「涉及资产」。

## 卡住了怎么办

某段代码看不懂它在做什么时，问题 1 按 **yes** 答（宁可高估档位），依据写「未能确认，按核心处理」，并在 `gaps.json` 登记一条缺口。
