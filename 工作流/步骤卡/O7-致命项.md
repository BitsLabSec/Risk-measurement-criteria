# O7 致命项

## 这一步在做什么

登记可能让业务分直接记 0 的**致命事实**。你只登记候选和证据，**是否触发由人确认**。

| 编号 | 致命事实 |
| --- | --- |
| X1 | 一把密钥在 24 小时内就能处分该业务全部用户资产 |
| X2 | 关键估值输入可以被低成本操纵，并能影响该业务全部资产 |
| X3 | 部署或配置错误，导致全部用户的核心必要操作完全失效，且没有恢复路径 |

规则来自[链上安全评估标准](../../onchain/链上安全评估标准.md)第 7 节；各业务的典型形态见专项第 5 节。

## 开始前你需要

- `O6-funds.json` 已通过检查

## 产出

`O7-fatal.json`。没有候选就填 `{"fatal": []}`。

## 操作步骤

1. **先运行检查。**
   ```bash
   python3 工作流/scripts/bitsscore.py validate 评估记录/<项目>/<评估ID> --step O7
   ```
   脚本会根据 O4 自动找出 X1 候选：H1 路径、只要 1 把密钥、有效延时不到 24 小时、能处分全部资产。每个候选都必须登记一条，`path_id` 写那条路径。
2. **找 X2 候选。** 看 O6 的 D1 检查和专项第 5 节的例子。主要抵押品或份额净值，是否直接用某个池子的现货价格？
   - 只有在有证据时才登记：价格的实际使用路径，以及操纵所需资金与可获利金额的对比。
   - 「可能被操纵」不算。
3. **找 X3 候选。** O5 或 O6 里有 `q_hard: yes`，并且影响**全部用户**的**核心必要操作**、又没有恢复路径的，登记一条。
4. 每条候选：`human_decision` 一律填 `pending`，`human_reviewer` 写 `无`。由人改成 `confirmed` 或 `rejected`，并写上自己的名字。

## 怎么判断

| 情况 | 是不是致命项 |
| --- | --- |
| EOA 持有 UpgradeCap，没有时间锁 | X1 候选 |
| 1/N 多签能升级，延时 12 小时 | X1 候选（1 把密钥、不到 24 小时） |
| EOA 能转走奖励金库，但奖励金库只是业务资产的一部分 | 不是 X1（不是全部资产），已在 O4 按 H1 计 0 分 |
| 价格源错绑，导致所有市场都无法清算 | X3 候选 |
| 只有部分市场无法清算 | 不是 X3 |
| 缺证、推断、「可能」 | 都不登记 |

## 填写示例

```json
{
  "fatal": [
    {"id": "XF01", "kind": "X1", "business_ids": ["BZ01", "BZ02"], "path_id": "PA01",
     "fact": "UpgradeCap 由单个 EOA 持有，没有时间锁，升级可替换全部记账逻辑",
     "evidence": ["https://suiscan.xyz/mainnet/object/0x…"],
     "human_decision": "pending", "human_reviewer": "无"}
  ]
}
```

## 完成检查

```bash
python3 工作流/scripts/bitsscore.py validate 评估记录/<项目>/<评估ID> --step O7
```

## 常见错误

- 自己把 `human_decision` 填成 `confirmed`。这一项只能由人填。
- 没登记脚本提示的 X1 候选。脚本找到的候选必须登记；觉得不该触发，就在 `fact` 里写清理由，交人判断。

## 卡住了怎么办

拿不准算不算致命项：照样登记成候选，写清楚拿不准的地方，交人判断。
