# P1 锁定生产部署

## 这一步在做什么

确认**在评估时点**，用户调用的是哪些入口，这些入口**实际执行**的是哪份代码。后面所有判断都以这份代码为准，而不是 GitHub 上的 `main` 分支。

## 开始前你需要

- `T0-task.json` 已通过检查
- 能访问链的 RPC 节点（下面给出了公共节点）

## 产出

`P1-baseline.json`，里面有两部分：

- `snapshots`：每条链一个快照（区块号或检查点号）
- `deployments`：每个「入口 → 实际执行代码」一条记录

## 操作步骤

1. **固定快照。** 对每条链取当前最新的区块或检查点，记下号码、哈希和时间。后面所有链上读数都用这个快照。
2. **找入口。** 从 T0 的 `known_entries` 出发；再查该协议最近的真实用户交易，看交易实际调用了哪个地址或包。只以交易里实际调用的对象为准。
3. **找实际执行的代码。** 每个入口都要判断它是不是代理，按下面的「怎么拿」查出实际执行的实现。
4. **每个入口填一条 `deployments`。** 多个入口指向同一份实现，也要每个入口各填一条。
5. **判断 `status`。** 见「怎么判断」。

## 怎么拿

### Sui

Sui 的公共 JSON-RPC 已经停用，统一用工作流自带的读取工具（基于 Sui GraphQL）。每次读取都会把原始响应存进评估目录的 `证据/raw/`，并打印可以直接填进 `evidence` 的引用。

```bash
R=工作流/scripts/sui_read.py
D=评估记录/<项目>/<评估ID>
# 1. 定快照：最新检查点的编号、digest、时间
python3 $R $D checkpoint
# 2. 包的全部版本：最后一行就是当前版本和它的包 ID
python3 $R $D package <原始包ID>
# 3. 升级凭证 UpgradeCap：package 字段指向当前实际执行的包，version 是版本号
python3 $R $D object <UpgradeCap 对象ID> --at <检查点> --name upgradecap
# 4. 真实用户交易：在快照前碰过某个常用共享对象（例如最大的池子、全局配置）的最近 25 笔交易里，
#    找一笔直接调用了当前包的，打印它调用的函数和 tx: 证据
python3 $R $D usertx <常用共享对象ID> --at <检查点> --pkg <当前包ID> --name usertx
```

很多交易是通过第三方合约间接调用的，交易里看不到目标包；`usertx` 只认**直接**调用。最近 25 笔都没有直接调用时，换一个对象再试。

原始包 ID 和 UpgradeCap 的对象 ID 通常写在项目仓库里（例如 `Published.toml`、安全说明文档），或者用第 2 条命令列出的首个版本的发布交易去找。

**Sui 的特点**：包升级后会生成一个**新的包 ID**，旧包 ID 仍然存在。因此：

- `entry` 填用户交易实际调用的包 ID；
- `actual_code` 也填这个包 ID；
- `proxy_kind` 填 `sui_package`；
- `version` 填第 2 条命令列出的当前版本号，并用第 3 条命令的 UpgradeCap 核对。

如果同时有新旧两个版本在被调用，各填一条。

### EVM

公共节点：各链官方或常用的公共 RPC（例如以太坊主网的 `https://ethereum-rpc.publicnode.com`）。

```bash
# 1. 最新区块（返回 number、hash、timestamp）
curl -s <RPC> -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"eth_getBlockByNumber","params":["latest",false]}'

# 2. EIP-1967 代理的实现地址（返回值的最后 40 位十六进制就是实现地址）
curl -s <RPC> -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"eth_getStorageAt","params":["<入口地址>","0x360894a13ba1a3210667c828492db98dca3e2076cc3735a920a3ca505d382bbc","<区块号十六进制>"]}'

# 3. Beacon 代理：先读 beacon 地址，再调用 beacon 的 implementation()
curl -s <RPC> -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"eth_getStorageAt","params":["<入口地址>","0xa3f0ad74e5423aebfd80d3ef4346578335a9a72aeaee59ff6cb3582b35133d50","<区块号十六进制>"]}'
```

在区块浏览器（如 Etherscan）的合约页上，如果显示 "Read as Proxy"，也能看到实现地址，可以用来交叉核对。

- 第 2 条返回全 0：不是 EIP-1967 代理，再试第 3 条。
- 两条都是 0：在浏览器上看合约是否标为代理；都不是，`proxy_kind` 填 `none`，`actual_code` 等于 `entry`。

## 怎么判断

| `status` 填什么 | 条件 |
| --- | --- |
| `confirmed` | 你有链上证据：真实交易调用了 `entry`，并且 `actual_code` 是用上面的方法在这个快照读出来的 |
| `unconfirmed` | 缺任何一项。例如只有项目文档里写的地址，没有找到真实交易；或者代理槽位读取失败 |

**`unconfirmed` 会导致代码安全结果变成「无法评分」。** 宁可如实填写 `unconfirmed`，也不要为了往下走而填 `confirmed`。

```json
  }],
  "deployments": [{
    "id": "I01",

    "status": "confirmed"
  }]
}
```

## 完成检查

```bash
python3 工作流/scripts/bitsscore.py validate 评估记录/<项目>/<评估ID> --step P1
```

## 常见错误

- 把 GitHub 上的地址当作生产地址，没有用真实交易验证。
- EVM 只记了代理地址，没有读实现地址。
- Sui 只记了最早的原始包 ID，没有记用户实际调用的最新包 ID。

## 卡住了怎么办

找不到真实交易，或者读不出实现地址时：`status` 填 `unconfirmed`，并在 `gaps.json` 登记一条缺口：`step` 填 `P1`，`blocks_denominator` 填 `true`。然后继续做后面能做的步骤。
