# C5 总体评价

## 这一步在做什么

总体评价从**基准 5 分**开始，按「找补项」加分、按「扣分项」减分，结果限定在 0–10。它的用途是：

- **找补**：审计做得扎实的项目，即使有少量审计后的小改动没覆盖到，也能把分数补回来；
- **扣分**：该审的都审了，但代码写法很反常的项目，扣一点分。

你只回答几个是非题，并记录反常写法的线索。A4 和 B2 由脚本自动判定；B1 是否扣分**由人来确认**，你不做这个决定。

规则来自[代码安全评分标准 v1.1](../../code-security/code-security-rating-standard.md) 第 3 节第 5 步，两处内容必须一致。

## 开始前你需要

- C4 已完成
- 已经运行过 `coverage`

## 产出

`C5-overall.json`

## 总表

| 编号 | 类型 | 分值 | 谁来判 | 你要做什么 |
| --- | --- | ---: | --- | --- |
| A1 | 找补 | +1 | 你 | 回答 `a1_multi_firm` |
| A2 | 找补 | +1 | 你 | 回答 `a2_incremental_review` |
| A3 | 找补 | +1 | 你 | 回答 `a3_formal_verification` |
| A4 | 找补 | +2 | 脚本 | 不用填 |
| B1 | 扣分 | −2 | 人 | 记录线索 `b1_observations`，`b1_human_decision` 填 `pending` |
| B2 | 扣分 | −1 | 脚本 | 不用填 |
| B3 | 扣分 | −2 | 你 | 回答 `b3_unaudited_cross_module` |

找补项合计最多 +5。

## 操作步骤

**A1：核心模块是否被 2 家及以上不同机构审计过？**
看 C2 的报告清单。如果核心档（P4 中问题 1 答 yes 的职责）所在的文件，被两家**不同机构**的报告的范围覆盖过，答 `yes`；`a1_evidence` 写机构名和报告 ID。同一家机构审了两次，不算。

**A2：是否有针对升级的增量审计或复审？**
C2 里有 `type` 为 `incremental_audit` 的报告，或者有一份报告明确写了它复审的是某次升级的改动，答 `yes`；`a2_evidence` 写报告 ID 和它复审的升级。

**A3：核心逻辑是否有形式化验证？**
C2 里有 `type` 为 `formal_verification` 的报告，并且它验证的函数属于核心档，答 `yes`；`a3_evidence` 写报告 ID 和被验证的函数。

**B3：是否有核心业务的跨模块调用链没有被任何一份报告完整审过？**
对 P3 的每个业务，找出它的核心档代码分布在哪些文件里。如果这些文件分布在两个以上，却没有任何一份报告的范围同时包含其中所有文件，答 `yes`；`b3_evidence` 写业务、模块，以及各报告分别审了哪些文件。

**B1：记录反常写法的线索。**
在核心档代码里留意下面这些写法。每发现一处，在 `b1_observations` 里记一条：

| `signal` | 线索 | 例子 |
| --- | --- | --- |
| `custom_math` | 自己实现了标准库或常用库已有的数学功能 | 手写定点数、手写 `mul_div`、自己实现开方 |
| `custom_auth` | 自己实现了一套权限框架，而没有用平台惯用的方式 | Sui 上不用 Cap 对象而用地址白名单；Solidity 不用 OpenZeppelin `AccessControl` 而自己写 |
| `bypass_framework` | 绕开了框架提供的安全机制 | 直接操作底层存储；绕过 `Balance`/`Coin` 的类型保护 |
| `unexplained_branch` | 无法解释的特殊分支或魔法数字 | `if (user == @0x1234) { ... }`、没有注释的硬编码常量 |
| `other` | 其他你觉得反常的写法 | 在 `description` 里写清楚 |

- 有线索时，`b1_human_decision` 填 `pending`，`b1_human_reviewer` 填 `无`。之后由人决定改成 `deduct`（扣 2 分）或 `no_deduct`，并填上确认人。
- 没有线索时，`b1_observations` 填 `[]`，`b1_human_decision` 填 `not_applicable`。
- **你不能自己填 `deduct` 或 `no_deduct`。**

## 填写示例

```json
{
  "a1_multi_firm": "yes",
  "a1_evidence": "AR01 OtterSec、AR02 MoveBit 都审了 lending.move、logic.move",
  "a2_incremental_review": "yes",
  "a2_evidence": "AR03 复审了 v11→v12 的升级",
  "a3_formal_verification": "no",
  "a3_evidence": "无",
  "b1_observations": [
    {"signal": "custom_math", "location": "lending_core/sources/math.move:10-80", "description": "自己实现了 ray 精度的乘除，没有使用 Sui 标准库或成熟的数学库"}
  ],
  "b1_human_decision": "pending",
  "b1_human_reviewer": "无",
  "b3_unaudited_cross_module": "no",
  "b3_evidence": "无"
}
```

## 完成检查

```bash
python3 工作流/scripts/bitsscore.py validate 评估记录/<评估ID> --step C5
```

## 交给人确认

如果 `b1_human_decision` 是 `pending`，C6 的结果会显示「待人工确认」，`C6-score.md` 里会列出全部线索。把这份文件交给人。人改好 `b1_human_decision` 和 `b1_human_reviewer` 后，再运行一次 `score`。

## 常见错误

- 同一家机构审了两次，A1 答了 yes。
- 自己决定 B1 扣不扣分。
- 为了加分，把只审了单个模块的报告说成覆盖了跨模块调用。
