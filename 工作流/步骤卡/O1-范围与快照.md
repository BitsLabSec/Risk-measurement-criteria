# O1 范围与快照

## 这一步在做什么

定下四件事：

1. 每条链在**哪个时点**读数（快照）；
2. 前期准备记录的代码，在这个时点是不是还在用；
3. 评哪些业务，每个业务有哪些**必要操作**和**市场**；
4. 前期准备关系图里的每个模块，对应链上哪些**顶层对象**。

后面所有读数都必须在这里定下的快照上读。

## 开始前你需要

- T0–P5 已完成，`validate <目录> --step P5` 通过
- 每个业务对应的专项文件（见 [onchain/README](../../onchain/README.md)）

## 产出

`O1-scope.json`

## 操作步骤

1. **定快照。** 每条链取一个最新的已确认区块或检查点，记录编号、哈希和时间。取法同 [P1](./P1-锁定生产部署.md) 第 1 步。
2. **复核基线。** 对 P1 的每个部署实例，在快照上重新读一次实际执行的代码：
   - Sui：读包对象的 `version`；
   - EVM 代理：读 EIP-1967 实现槽位。

   和 P1 记录的一致，`unchanged` 填 `yes`。不一致，填 `no` 并停下：代码已经变了，前期准备要按新代码重做。
3. **列业务。** P3 里的每个业务一条。不评的业务写进 `out_of_scope`，并写原因。
4. **抄必要操作。** 打开这个业务的专项文件，把第 1 节「必要操作」表里的每一行抄进 `necessary_ops`，并找到对应的入口函数。专项里写「如机制提供」的操作，协议没有就不抄。
5. **列市场。** 业务内有多个独立的市场或池子（例如借贷的每个资产储备、DEX 的每个池子），每个写一条 `markets`。只有一个整体的，`markets` 留空 `[]`。市场没有独立对象、只是表中的一个条目时（例如 NAVI 的储备），`object` 写表的 ID，`key` 写条目的键。
   - DEX 不全量列池子。按 DEX 专项第 0 节，只列明确选定的池，并在 `out_of_scope` 写明其余池子没有纳入。
   - **市场清单从哪里来**：优先从链上的市场列表读（例如借贷的储备列表、注册表对象），`discovered_by` 填 `onchain_registry`。链上无法枚举时（例如 EVM 的 mapping，key 只出现在事件里），**不要去扫事件**，改从官方文档或前端拿清单，`discovered_by` 填 `official_list`。交付物会注明「清单可能不完整」。

6. **登记模块对应的链上对象。** 以 P6 关系图为线索，对每个模块填 `module_objects`：它的包或合约，以及它用到的顶层共享对象（全局配置、注册表、管理员凭证、金库）。
   - **只看最顶层。** 不逐个列池子、仓位、用户对象。DEX 的成千上万个池子共用同一个全局配置和工厂，登记这两个就够了。
   - 外部依赖模块（预言机等）也登记它的价格对象或合约。

## 怎么判断

| 情况 | 怎么填 |
| --- | --- |
| 借贷：每个资产有自己的参数和余额 | 每个资产储备一个市场 |
| 金库：多个金库共用一套合约 | 每个金库一个市场 |
| Farming：多个奖励池共用一个金库 | 没有独立的余额，不分市场，`markets` 留空 |
| 代币：只有一个币 | 不分市场 |

## 完成检查

```bash
python3 工作流/scripts/bitsscore.py validate 评估记录/<项目>/<评估ID> --step O1
```

## 常见错误

- 用了 P1 的旧快照。链上评估要用新的快照，并复核基线。
- 把「开新仓」「新增存款」当成必要操作。必要操作是用户**保住已有权益**要做的事。

## 卡住了怎么办

业务的专项是 `other`，或者看不出该用哪个专项：在 `gaps.json` 登记（`step` 填 `O1`，`blocks_denominator` 填 `true`），交人决定。
