# C2 登记审计报告

## 这一步在做什么

把所有适用的审计报告和形式化验证报告找出来。对每份报告登记三件事：

- 审的是**哪个版本**（commit）；
- 审了**哪些文件**；
- 受审版本的源码在本地**放在哪里**。

脚本会拿这个受审版本和生产版本逐行比对。

## 开始前你需要

- C1 已完成

## 产出

`C2-reports.json`：

- `reports`：每份报告一条
- `search_log`：每次查找一条，找到和没找到都要记

## 操作步骤

1. **查找报告。** 以下渠道都要查，每查一个渠道就在 `search_log` 里记一笔：
   - 项目官网的 Security、Audits 页面和文档站；
   - 项目 GitHub 仓库的 `audits/`、`audit/` 目录和 README；
   - 审计机构官网的报告列表（例如 OtterSec、MoveBit、Zellic、OpenZeppelin、Trail of Bits、Certik、Halborn、Asymptotic）；
   - DefiLlama 上该项目页面的 Audits 链接。
2. **打开每份报告，找到 Scope 部分**，记下：
   - 仓库地址和 commit。报告里一般写成 "Commit hash" 或 "Version"；
   - 范围内的文件列表；
   - 明确排除的内容；
   - 是不是只审了部分函数或 PR 差异。
3. **把受审版本放到本地。**
   - 受审 commit 在 P2 的同一个仓库里：`kind` 填 `git`，`repo_path` 填 P2 的 `local_path`，`commit` 填受审 commit。
   - 受审 commit 在另一个仓库：先 clone 那个仓库，`repo_path` 填新 clone 的目录。
   - 项目方直接给了受审源码包：解压后 `kind` 填 `dir`，`dir_path` 填解压目录。
   - 报告没写 commit，或者 commit 找不到：`kind` 填 `unavailable`。这份报告覆盖的行会全部记为「未覆盖」（原因 `no-diff`）。
4. **范围里的每个文件写一条 `scope`。**
   - `audited_path`：受审版本里的路径；
   - `production_path`：生产版本里的路径。文件没改名就和 `audited_path` 一样；改了名就填新名字；生产版本里已删除的文件不用登记；
   - 报告只审了部分行：在 `only_line_ranges` 里填受审版本的行区间，例如 `[[100, 250]]`；审了整个文件就填 `[]`；
   - 报告明确排除的行：填在 `excluded_line_ranges` 里。

## 怎么判断

| 情况 | 怎么登记 |
| --- | --- |
| 文件出现在报告的 Scope 表里 | 登记到 `scope` |
| 文件只在发现、依赖列表或附录里被提到 | **不登记** |
| 报告写着 "Scope: PR #123" | 只登记这个 PR 改过的文件，并在 `only_line_ranges` 里填改动区间 |
| 一份终审报告引用了初审和多轮复审 | 每一轮各登记一份报告，各自用自己的 commit |
| 形式化验证报告 | `type` 填 `formal_verification`，`only_line_ranges` 只填被验证的函数所在的区间 |

## 填写示例

```json
{
  "reports": [{
    "id": "AR01", "firm": "OtterSec", "type": "audit", "date": "2025-03-10",
    "url": "https://.../navi-audit.pdf",
    "audited_source": {"kind": "git", "repo_path": "/work/navi-src", "commit": "<受审 40 位 commit>", "dir_path": "无"},
    "scope_evidence": "第 4 页 Scope 表",
    "scope": [
      {"audited_path": "lending_core/sources/lending.move", "production_source_id": "S01",
       "production_path": "lending_core/sources/lending.move", "only_line_ranges": [], "excluded_line_ranges": []}
    ]
  }],
  "search_log": [
    {"target": "lending_core", "channels": ["https://naviprotocol.io/security", "https://github.com/naviprotocol/navi-smart-contracts/tree/main/audits"],
     "date": "2026-11-25", "found_report_ids": ["AR01"]}
  ]
}
```

## 完成检查

```bash
python3 工作流/scripts/bitsscore.py validate 评估记录/<项目>/<评估ID> --step C2
```

检查会确认三件事：受审 commit 确实存在于 `repo_path` 仓库中；`production_path` 在生产源码中存在；`search_log` 不为空。

## 常见错误

- 把审计机构的营销页面当成报告。
- 用报告日期去猜 commit。commit 必须来自报告原文。
- 漏记没找到报告的查找。「没找到」也是证据。

## 卡住了怎么办

找不到受审 commit 时，`kind` 填 `unavailable`，在 `gaps.json` 登记缺口（`step` 填 `C2`，`blocks_denominator` 填 `false`），然后继续往下做。
