# P5 角色与控制

## 这一步在做什么

找出代码中所有**特权角色**（谁有特殊权限），以及每个角色能执行的**特权操作**（控制）：改了什么、在哪里生效、影响哪些职责。链上权限评估会直接用到这张表。

## 开始前你需要

- `P4-responsibilities.json` 已通过检查

## 产出

`P5-roles-controls.json`：

- `roles`：每个角色或权限凭证一条
- `controls`：每个特权函数一条

## 操作步骤

1. **找权限检查。** 在源码目录运行：
   ```bash
   # Move：以 Cap 结尾的类型（Sui 常用 Cap 对象表示权限）、地址比较
   grep -rnE "struct \w*Cap\b|: &\w*Cap|&mut \w*Cap|tx_context::sender\(ctx\) ==|assert!\([^)]*sender" <源码目录> --include=*.move
   # Solidity：修饰器、角色、msg.sender 比较
   grep -rnE "modifier \w+|onlyOwner|onlyRole|hasRole|require\(msg\.sender ==|_checkOwner|AccessControl" <源码目录> --include=*.sol
   ```
2. **每种凭证建一个角色。** 例如 `AdminCap`、`OwnerCap`、`onlyOwner`、`DEFAULT_ADMIN_ROLE`。
   - `check_locations`：每个做这项检查的位置。
   - `how_obtained`：这个权限怎么来的，查 `init` 函数、构造函数、`grant`/`transfer` 函数。
   - `granted_by_role_ids`：哪个角色能授予它。例如 `StorageAdminCap` 能铸造 `OwnerCap`，那么 `OwnerCap` 这一条就填 `StorageAdminCap` 对应的角色 ID。
3. **每个需要权限的函数建一个控制。** 从第 1 步搜到的每个位置出发，找到所在的函数，按下表填写。
4. **升级权限也是角色。**
   - Sui：`UpgradeCap`；
   - EVM：代理的 admin 或 owner，以及 `upgradeTo` 的调用权。

   这两类都要建角色和控制，控制的 `consequence` 一般填 `H1`。

## 怎么判断

**`consequence`（最坏后果）**

| 选项 | 条件 | 例子 |
| --- | --- | --- |
| `H1` | 能任意转走用户资产、改写用户记录，或者升级合约（换掉逻辑） | 提走池内资金、修改债务、`upgrade` |
| `H2` | 能在限定范围内改变**已有**用户的条件 | 调清算线、调费率（有上限）、换价格源 |
| `H3` | 能让用户的还款、取款、撤资等必要操作停下来 | 暂停开关、冻结 |
| `none` | 只影响新增业务，或者不影响用户 | 调整新币上架参数、改事件 |

一个函数可能造成多种后果时，选最严重的：H1 > H2 > H3 > none。

**`reachability`（能不能走通）**

| 选项 | 条件 |
| --- | --- |
| `source_closed` | 从源码看，持有凭证就一定能执行 |
| `config_dependent` | 要满足某个配置或状态才能执行，例如需要先打开某个开关 |
| `disabled_in_code` | 代码里明确禁用了，例如函数体只有 `abort` |
| `unknown` | 没查清 |

**`effect_locations`（生效位置）**

- 直接生效的（例如直接转账）：写执行那一行。
- 先写入状态、之后才生效的（例如写入 `paused`，借款时再读取）：**写入的位置和读取的位置都要写**。

## 填写示例

```json
{
  "roles": [
    {"id": "R01", "credential": "storage::OwnerCap", "check_locations": ["lending_core/sources/storage.move:323-330"],
     "how_obtained": "init 时给发布者；R02 可调用 mint_owner_cap 再铸造", "granted_by_role_ids": ["R02"]},
    {"id": "R02", "credential": "storage::StorageAdminCap", "check_locations": ["lending_core/sources/storage.move:822-830"],
     "how_obtained": "init 时给发布者", "granted_by_role_ids": []}
  ],
  "controls": [
    {"id": "K01", "role_ids": ["R01"], "entry": "storage::set_pause",
     "conditions": "校验 Storage 版本", "what_changes": "Storage.paused",
     "effect_locations": ["lending_core/sources/storage.move:323-330", "lending_core/sources/lending.move:363-363"],
     "affected_responsibility_ids": ["D01"], "consequence": "H3", "reachability": "source_closed"}
  ]
}
```

## 完成检查

```bash
python3 工作流/scripts/bitsscore.py validate 评估记录/<评估ID> --step P5
```

## 常见错误

- 漏掉间接授权：A 能授予 B，B 能暂停，那么 A 也间接能暂停。`granted_by_role_ids` 一定要填。
- 漏掉升级权限。
- 把只影响新开仓的参数判成 H2。

## 卡住了怎么办

授予路径追不清时，`how_obtained` 写「未查清」，`reachability` 填 `unknown`，并在 `gaps.json` 登记缺口。
