# T0 任务单

## 这一步在做什么

把委托方交代的任务记下来：评哪个项目、评哪几个维度、涉及哪些链、范围是什么。后面所有步骤都以这份任务单为准。

## 开始前你需要

- 委托方给的项目信息，例如项目名、官网、合约地址、仓库链接、要评的业务
- 已经运行过 `init`，评估目录下有空白模板

## 产出

`T0-task.json`

## 操作步骤

1. `assessment_id` 填 `<项目英文名小写>-<年月日>`，例如 `navi-20261125`；同一天第二次评估加 `-2`。评估目录必须是 `评估记录/<项目>/<评估ID>/`，目录名和评估 ID 一致。
   - 第一次评估这个项目：`previous_assessment_id` 写 `无`，`reason` 填 `first`。
   - 重评：**新建一个目录**，不要改旧目录。`previous_assessment_id` 写上一次的评估 ID，`reason` 按下表选。可以把上一次的文件复制过来作为起点，但每一步都要重新核对并通过检查。

   | `reason` | 什么时候用 |
   | --- | --- |
   | `scheduled` | 定期复评 |
   | `permission_change` | 权限持有人或门限变了 |
   | `upgrade` | 合约升级 |
   | `parameter_change` | 核心参数改了 |
   | `rule_change` | 评分规则升了版本 |
   | `correction` | 纠正上一次的错误 |
2. `project` 填项目名称。
3. `dimensions`：只评代码安全，填 `["code_security"]`；两个维度都评，填 `["code_security", "onchain"]`。
4. `chains`：项目部署在哪几条链上，就每条链写一项。链 ID 的写法见[工作流 README](../README.md#填写格式约定)。
5. `scope_statement`：**原样**抄写委托方对范围的说法。没有书面说法的，写「委托方口头：……」。
6. `known_entries`、`known_repos`：把委托方给的地址和仓库原样列出。这些只是线索，P1、P2 还要核验。
7. `out_of_scope`：委托方明确说不评的内容；没有就填 `[]`。
8. `assessor` 填你的名字，`date` 填今天的日期。

## 填写示例

```json
{
  "assessment_id": "navi-20261125",
  "previous_assessment_id": "无",
  "reason": "first",
  "project": "NAVI Protocol",
  "dimensions": ["code_security"],
  "chains": [{"chain_id": "sui:mainnet", "name": "Sui Mainnet"}],
  "scope_statement": "委托方邮件：评估 NAVI 借贷核心（lending_core）及其预言机模块",
  "known_entries": ["0x<包ID>"],
  "known_repos": ["https://github.com/naviprotocol/navi-smart-contracts"],
  "out_of_scope": ["前端", "NAVI 聚合器"],
  "assessor": "agent-01",
  "date": "2026-11-25"
}
```

## 完成检查

```bash
python3 工作流/scripts/bitsscore.py validate 评估记录/<项目>/<评估ID> --step T0
```

## 常见错误

- 自己扩大或缩小范围。范围以委托方的说法为准；有疑问时，在 `scope_statement` 里写明疑问，并交给人确认。

## 卡住了怎么办

委托方没有给出范围时，停下来，向人确认范围。不要自己定范围。
