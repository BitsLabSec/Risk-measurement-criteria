# C4 登记发现

## 这一步在做什么

把每份报告里的每条发现（finding）都登记下来，并回答三个问题：

1. 它有多严重？
2. 它在当前生产代码里还存在吗？
3. 它被修好并且经过审计方复核了吗？

脚本据此决定分数封顶。

## 开始前你需要

- C3 已完成

## 产出

`C4-findings.json`：每条发现一条，Informational 等级的也要登记。

## 操作步骤

对每份报告的每条发现：

1. 抄写 `finding_id`、`title` 和报告给的等级 `severity`。
2. 报告没有给等级时，`severity` 填 `unrated`，并按下面的定级表自己定级，填在 `assessor_severity`，同时写明理由。报告已经定了级的，`assessor_severity` 填 `same`。
3. 判断 `production_applicable`，见下表。
4. 判断 `fix_status`，见下表。
5. 判断 `centralization_only`：如果这条发现只是在说「某个管理员权限过大」，而没有指出代码写错了，就填 `true`。

## 怎么判断

**`production_applicable`（在当前生产代码里还存在吗）**

| 填 | 条件 |
| --- | --- |
| `yes` | 在生产源码（P2 的 commit）里，找到了报告指出的那段有问题的代码，而且问题仍然成立 |
| `no` | 生产源码里那段代码已经被改掉或删除，问题不再成立。`applicability_evidence` 写现在的逻辑，`applicability_refs` 写现在的代码位置 |
| `unknown` | 找不到对应的代码，或者判断不了 |

**`fix_status`（修复状态），从上往下，取第一个符合的**

| 填 | 条件 |
| --- | --- |
| `fixed_and_reviewed` | 报告或后续复审报告明确写了 "Fixed" / "Resolved"，**并且**写出了修复 commit，**并且**这个修复包含在生产 commit 里 |
| `fix_deployed_not_reviewed` | 修复代码在生产 commit 里，但审计方没有复核 |
| `claimed_fixed` | 只有项目方声称已经修复 |
| `acknowledged` | 报告写的是 "Acknowledged"，项目方接受风险，不修 |
| `not_fixed` | 其他情况 |

检查修复 commit 是否包含在生产 commit 里：

```bash
git -C <P2的local_path> merge-base --is-ancestor <修复commit> <生产commit> && echo 包含
```

**报告未定级时的定级表**

| 等级 | 条件 |
| --- | --- |
| `critical` | 无需权限就能直接盗取或永久冻结用户资金 |
| `high` | 无需权限就能造成资金损失，但需要特定条件；或者能让核心功能长期不可用 |
| `medium` | 需要特定权限或罕见条件才能造成损失；或者能让部分功能不可用 |
| `low` | 影响很小，或者几乎不可能触发 |
| `informational` | 代码风格、建议类 |

## 脚本怎么用这些信息

同时满足以下三条的发现参与封顶：`production_applicable` 是 `yes`，`fix_status` 不是 `fixed_and_reviewed`，`centralization_only` 是 `false`。取其中最高的等级封顶：Critical 封 0 分，High 封 49 分，Medium 封 79 分，Low 封 94 分。

`unknown` 的发现不参与封顶，但会在结果里单独列出来。

## 填写示例

```json
{
  "report_id": "AR01", "finding_id": "OS-NAVI-ADV-02", "title": "清算奖励计算可被绕过",
  "severity": "high", "assessor_severity": "same", "assessor_severity_reason": "无",
  "production_applicable": "no", "applicability_evidence": "已改为先计算奖励再扣押",
  "applicability_refs": ["lending_core/sources/logic.move:610-625"],
  "fix_status": "fixed_and_reviewed", "fix_evidence": "报告第 12 页写明 Resolved in abc1234；abc1234 是生产 commit 的祖先",
  "fix_refs": ["https://github.com/<org>/<repo>/commit/abc1234"],
  "centralization_only": false, "root_cause_group": "无"
}
```

## 完成检查

```bash
python3 工作流/scripts/bitsscore.py validate 评估记录/<项目>/<评估ID> --step C4
```

## 常见错误

- 看到 "Acknowledged" 就当成已修复。
- 项目方说修了，就填 `fixed_and_reviewed`。
- 漏登记 Informational 等级的发现。

## 卡住了怎么办

判断不了是否仍然存在时，`production_applicable` 填 `unknown`，`applicability_evidence` 写清楚卡在哪里，`applicability_refs` 写你查过的代码位置或链接。修复状态是已修复的，`fix_refs` 必须给出修复提交、部署交易或复核报告的链接。
