# BitsScore 代码安全评分标准

- 版本 v1.1，2026-11-25
- 依据：[评分骨架 v1.0](../评分骨架.md) 第 2 节。本文与骨架冲突时，以骨架为准。
- 历史版本：[v0.9](./archive/code-security-rating-standard-v0.9.md)，只用于复算旧结果。
- 执行方式：[工作流](../工作流/README.md)的步骤卡 C1–C6。计分由 `工作流/scripts/bitsscore.py` 按本标准实现；本文与脚本不一致时，以本文为准，并修正脚本。

## 1. 回答的问题

当前生产部署的代码中，有多少已被适用的审计覆盖？还有没有未解决的已知风险？

## 2. 输入

从[前期准备](../前期准备/assessment-preparation.md)取得以下内容：

- 部署基线 ID、各部署实例和已核验的生产源码（完整 commit 或归档哈希）
- 代码职责清单及各职责的 5／3／1 档位和源码位置

外部合约和第三方库不计入分子，也不计入分母；项目自己写的调用、适配、输入校验和资产交接逻辑要计入。

如果生产源码或职责档位无法核实，导致建不出分母，本轮结果记为「**无法评分**」，同时写明原因、受影响范围和已核实的部分。

## 3. 计分步骤

### 第 1 步　建分母

1. 统计范围内生产源码的**有效行**：去掉空行和纯注释行；代码后面带行尾注释的，仍算一行。记录统计工具及其版本。
2. 按职责的源码区间，把每一行归入核心（5）、重要（3）或辅助（1）档。一行同时属于多档时，取最高档。
3. 同一份实现被多个地址复用时，只计一次。不同的实现或版本分别计。
4. 已确认没有适用代码的档，记为「不适用」，从权重中移除。

### 第 2 步　收集报告

对每一份审计报告或形式化验证报告，登记以下内容：

| 字段 | 内容 |
| --- | --- |
| 报告 ID、机构、类型、日期 | 类型分为普通审计、增量审计、形式化验证 |
| 受审版本 | 仓库和完整 commit，或包版本。初审和复审的版本分开登记。 |
| 受审范围 | 报告正式范围里列出的文件或路径，以及排除项。只在发现、依赖列表或其他地方顺带提到的文件不算范围。 |
| 原文位置 | 链接和页码 |

- 正式范围里列出的文件，按整份文件计入审查范围，除非报告明确只审了 PR 差异或特定函数。
- 形式化验证只计入报告里实际验证过的路径。
- 某个模块找不到报告时，记录查过哪些渠道、查询日期，该模块的生产行全部算未覆盖。

### 第 3 步　逐行判定覆盖

每一行生产代码只有两种结果：**覆盖**或**未覆盖**。

**算覆盖的情况只有两种：**

1. **直接覆盖**：受审版本就是生产版本（或源码哈希一致），且这一行在报告的审查范围内。
2. **沿用覆盖**：受审版本是旧版本，且同时满足以下三条：
   1. 能拿到受审版本的源码，并能和生产版本做出 diff；
   2. 这一行在 diff 中没有改动（只改格式或只是位置移动，不算改动）；
   3. 这一行直接调用的函数、读写的状态字段，在 diff 中也没有语义改动。

其余情况一律算**未覆盖**，并记录原因标签：

| 原因标签 | 含义 |
| --- | --- |
| `no-report` | 没有找到覆盖这一行的报告 |
| `out-of-scope` | 有报告，但这一行不在报告范围内，或属于报告的排除项 |
| `changed` | 这一行相对受审版本有改动 |
| `dependency-changed` | 这一行本身没改，但它调用的函数或读写的状态有语义改动 |
| `no-diff` | 拿不到受审版本，做不出 diff |

补充规则：

- 多份报告覆盖同一行时，只计一次。
- 一行只要有任何一部分不满足覆盖条件，整行算未覆盖。
- 报告明确写了配置前提（例如「假设某参数小于 X」），而链上当前配置不满足时，受影响的行算未覆盖，原因记 `dependency-changed`。配置本身好不好，由链上评估评价。

### 第 4 步　算覆盖分（90 分）

```text
档覆盖率   = 该档覆盖行数 ÷ 该档有效行数
档满分     = 90 × 档权重 ÷ 适用档权重之和        （权重：核心 5，重要 3，辅助 1）
档得分     = 档覆盖率 × 档满分
覆盖分     = 各适用档得分之和
```

三档都适用时，各档满分依次为 50、30、10。如果辅助档不适用，核心和重要的满分分别为 56.25 和 33.75。

例：核心 100 行，其中 80 行覆盖；重要 50 行，全部覆盖；辅助 20 行，没有覆盖。覆盖分 = 0.8×50 + 1.0×30 + 0×10 = 70。

计算过程保留全部精度，结果展示到两位小数。

### 第 5 步　总体评价（10 分）

总体评价的主要用途是**找补**：
- 一个项目审计做得很扎实，只是少量审计后的小改动没被覆盖，可以在这里加分；
- 一个项目该审的都审了，但代码本身的写法很反常，可以在这里扣分。

从**基准 5 分**开始，按下表加减，结果限定在 0–10：

| 编号 | 类型 | 条件 | 分值 | 由谁判定 |
| --- | --- | --- | ---: | --- |
| A1 | 找补 | 核心模块被 2 家及以上不同机构审计过 | +1 | 评估人 |
| A2 | 找补 | 有针对升级的增量审计或复审 | +1 | 评估人 |
| A3 | 找补 | 核心逻辑有形式化验证 | +1 | 评估人 |
| A4 | 找补 | 核心档未覆盖的行全部来自审计后的小改动：原因只有改动或依赖改动，单处改动不超过 20 行，且没有新增受审版本中没有的函数或结构体 | +2 | 脚本 |
| B1 | 扣分 | 代码逻辑反常：自己实现标准库已有的安全功能、绕开框架机制、出现无法解释的特殊分支等 | −2 | 评估人列出线索，**由人确认** |
| B2 | 扣分 | 包含核心档代码的单个函数超过 200 有效行 | −1 | 脚本 |
| B3 | 扣分 | 有核心业务的跨模块调用链，没有被任何一份报告完整审过 | −2 | 评估人 |

```text
总体评价 = max(0, min(10, 5 + min(5, 找补项之和) − 扣分项之和))
```

- 覆盖明细照实记录，不因总体评价而改动。
- 执行方法见[工作流步骤卡 C5](../工作流/步骤卡/C5-总体评价.md)，计算由工作流脚本实现；两处与本表必须一致。

### 第 6 步　风险封顶

1. 列出所有报告中的发现，逐条判断两件事：
   - **生产是否适用**：这条问题在当前生产代码中是否仍然存在。结论为适用、不适用或无法确认。
   - **是否已修复**：只有修复代码已部署到生产，**并且**经过审计方复核确认，才算已修复。项目方声称修复、或者接受风险，都不算已修复。
2. 风险等级采用报告给出的等级。报告未定级的，由评估人按触发条件、所需权限、受影响资产和可恢复性来定级，并写明理由。
3. 在「生产适用且未修复」的发现中，取最高等级，按下表封顶：

| 最高等级 | 封顶 |
| --- | ---: |
| Critical | 0 |
| High | 49 |
| Medium | 79 |
| Low | 94 |
| 无 | 100 |

- 同一根因的多条发现合并为一条。
- 生产是否适用无法确认的发现，不参与封顶，但要在结果中单独列出。
- 纯中心化问题（例如 owner 权限过大）不在本维度封顶，交给链上权限评价。

### 第 7 步　最终分

```text
代码安全最终分 = min(覆盖分 + 总体评价, 封顶)
```

B1 有线索、但尚未经人确认时，结果为「待人工确认」，不出最终分。

## 4. 交付

### 4.1 一页结果

- 评估对象、部署基线 ID、评估日期
- 各档的有效行数、覆盖行数、覆盖率、满分和得分
- 未覆盖行数按原因标签汇总
- 总体评价分，以及命中的找补项和扣分项
- 封顶等级及对应的发现
- 最终分；或者「无法评分」，并写明原因

### 4.2 证据明细

| 表 | 每条记录的字段 |
| --- | --- |
| 报告清单 | 报告 ID、机构、类型、日期、受审版本、受审范围、排除项、原文位置 |
| 覆盖明细 | 基线 ID、职责 ID、档位、源码文件、行区间、覆盖或未覆盖、报告 ID（覆盖时填）、原因标签（未覆盖时填）、diff 链接（沿用时填） |
| 发现清单 | 报告 ID、发现 ID、等级、是否生产适用、是否已修复、修复和复核证据、是否参与封顶 |

覆盖明细中的行区间不能重叠，且合起来必须正好等于分母。

### 4.3 复核

另一位评估人应能做到：用覆盖明细加总出各档的覆盖行数；从任意一行追查到报告范围或 diff；从封顶追查到具体的发现。
