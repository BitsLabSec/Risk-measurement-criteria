# BitsScore Web3 业务攻防评级标准

- 记录日期：2026-11-06
- 文档版本：v0.5。
- 更新日期：2026-11-16。
- 所属范围：Web3 项目的业务流程与支撑系统安全能力评估，以实际业务流程为主线。
- 核验方式：以渗透测试为核心，结合适用的架构、配置及受控故障验证；不以“链下”限定业务交互边界。
- 证据基础：我们交付的最终渗透测试报告，或能够明确对应测试范围和结论的外部渗透测试报告。
- 职责：评级侧独立读取最终渗透报告及已有项目资料，完成范围映射、权重、关键验证项、适用性和分数判断；渗透服务按自身规范执行和交付，不承担评分工作。
- 规则性质：权重、分值和封顶条件为初始政策规则，尚未经样本统计校准，不是外部标准规定的分数，不代表攻击或损失概率。

## 1. 前提与整体方法

### 1.1 信任假设

对已完成约定范围测试、且获得通过结论的部分，评级侧暂认定其安全能力大致合格。评级直接采信最终交付结论，不重新审查渗透报告的方法或可信度，不把整改、复测次数和过程单列评分。

最终报告明确保留的风险、限制及未覆盖范围直接继承。不能将“有报告”解释为全部业务均已通过，也不能将未覆盖解释为已确认不安全。

不按漏洞数量、修复数量、测试工具数量、报告篇幅或测试次数加分。零发现与发现问题后完成修复，在最终适用覆盖和剩余风险相同的情况下受到相同待遇。

### 1.2 服务与评级的关系

```text
渗透服务：客户选择与授权确认 → 功能和模块测试 → 最终报告
评级侧：最终报告及已有项目资料 → 业务流程与覆盖映射
       → 固定权重和关键验证项 → 计算 C、G、R → 发布及适用性更新
```

渗透报告按“十项服务范围 × 七个维度”呈现，并披露实际对象、环境、授权、执行范围、限制和 Finding。评级采用“实际业务流程 × 适用检查维度”，由评级侧建立两者的对应关系。

十项服务是报告分类，不直接作为十个等权或固定权重的计分单元。前端、API、云、服务器、签名服务和发布流水线是业务涉及的对象；同一流程经过多个服务类别时合并使用适用证据，不重复增加流程或权重。

### 1.3 评级侧工作与留痕

| 工作 | 评级侧形成的记录 |
| --- | --- |
| 固定评估范围 | 从报告和已有项目资料识别实际业务、角色、资产、组件及必要管理路径；区分项目实际范围和本次委托范围，缺失处标待确认 |
| 读取覆盖事实 | 保留报告原服务编号、D1–D7 状态、未委托或不适用原因、执行范围、环境版本及来源位置，映射为流程检查记录 |
| 确定评分结构 | 根据实际业务影响固定流程权重、适用维度、关键验证项及其依据；记录本次评估版本和结构变化原因 |
| 继承终审风险 | 保留 Finding ID、所属及关联服务项目、实际影响流程、原始等级、类型和最终状态；建立范围及版本对应 |
| 计算与发布 | 判断当前适用性，形成 C、G、R、最终分或未知区间，并关联报告和依据 |

这些是评级工作底稿及发布信息，不要求测试人员计算、在报告中增补评分字段或按评级模板重交记录。已有报告范围清晰且结论明确时直接采信；资料不足时保留缺口，不为取得分数追加测试或推定结论。

## 2. 业务流程范围及模块边界

### 2.1 通用业务流程模板

| 业务流程 | 主要测试范围 | 典型组件 |
| --- | --- | --- |
| 身份建立与账户管理 | 钱包登录、绑定与解绑、角色、会话、账户或网络切换、身份恢复 | 前端、钱包连接、认证 API、后台 |
| 业务信息获取与决策 | 资产、余额、价格、收益、风险及交易条件的获取与展示；输入被篡改后的业务影响 | 前端、索引器、RPC、报价与路由 API |
| 授权与签名 | 签名用途、授权对象、额度、有效期、展示与实际请求的一致性及签名复用 | 前端、钱包、签名生成与验证服务 |
| 业务提交与执行 | 目标、收款人、资产、金额和链的绑定；参数篡改、步骤绕过及执行边界 | 前端、API、交易构造器、Relayer、相关合约接口 |
| 结果确认与后续处理 | 待确认、失败、回滚及结果归属；记账、发放、解锁等后续操作 | RPC、索引器、Webhook、后台状态及账目 |
| 特权操作与生产发布 | 管理业务配置、部署、发布、凭据和签名调用的完整控制路径 | 管理端、云平台、仓库、CI/CD、部署与签名服务 |
| 异常处置与恢复 | 业务故障、凭据失效、重启、恢复与回滚过程中身份、权限和业务状态的正确性 | 上述相关组件与实际恢复入口 |

根据项目真实业务展开模板，不要求所有项目具有相同组件或全部流程。例如 DEX 展开报价、授权、Swap、增减流动性；Lending 展开存款、抵押、借款、还款、提款；金库展开存入、份额展示、赎回申请及领取。

常规渗透中的注入、SSRF、越权、文件上传、秘密信息泄露等，结合实际流程和影响归入检查。无法自然归入用户业务的基础设施入口，归入支撑相关业务的管理／运维路径，不能因此遗漏。

### 2.2 与代码、链上评估的边界

| 范围 | 本标准如何处理 |
| --- | --- |
| 合约计算、链上验签与结算逻辑的正确性 | 归代码安全评估；链下测试验证请求生成、传递及跨系统使用过程，不重新完整审计合约 |
| 链上权限、参数、头寸及预言机当前状态 | 归相应链上模块；必要时作为业务测试输入，不重复评价同一链上配置 |
| 域名、托管、云账号、发布权限、后台及签名调用能力 | 属于本标准，按其影响的业务和控制路径测试；不局限于外部网络扫描 |
| 跨组件攻击 | 按完整业务后果记录，共享证据；同一问题经过多个组件不重复累计为多份风险 |
| 日常安全运营的补充信息 | 本标准未覆盖的安全联系、反馈政策、运营责任及沟通安排由 [安全运营与披露补充说明](../盘外情报/security-operations-disclosure-supplement.md) 整合呈现，不独立评分或要求追加验证；技术和业务路径继续按本标准评价，已有报告结论直接引用 |

本标准使用仍适用于当前系统的指定版本测试证据，结合范围与配置对应关系更新。它评价端到端业务攻防验证覆盖，不机械套用链上单 snapshot 模式；既不替代合约逻辑审计，也不按链上／链下位置切断跨系统业务链路。

### 2.3 十项报告服务与业务流程的对应

| 报告服务项目 | 评级侧对应的实际业务 | 映射要求 |
| --- | --- | --- |
| 1. 外部攻击面与敏感信息暴露 | 相关用户业务或管理运维路径 | 依据暴露入口及实际影响归入流程，资产枚举本身不代表流程已完成验证 |
| 2. Web 应用与 API 安全 | 实际承载的登录、查询、交易、退出或管理流程 | 按报告明确的功能和角色对应，不把整行已覆盖扩展到所有接口或业务 |
| 3. 身份认证与账户权限 | 身份建立与账户管理，以及依赖该身份的操作 | 身份证据仅复用于已明确适用的业务和角色边界 |
| 4. 钱包连接、授权与签名 | 身份、授权签名及相应执行流程 | 根据签名实际用途归类，不将登录签名验证推及全部交易签名 |
| 5. 交易构造、提交与执行 | 相应业务的提交与执行 | 明确交易对象、角色及执行到哪一步，不推定已覆盖后续记账或结算 |
| 6. 核心业务流程与业务规则 | 项目的存入、借还款、交易、赎回、领取等实际流程 | 根据报告实际范围展开，不将类别名称视为全部核心业务已测 |
| 7. 链上链下交互与异步任务 | 结果确认、后续处理及相关任务执行流程 | 对应消息、任务及业务状态的实际作用范围 |
| 8. 管理后台与特权执行路径 | 特权操作及必要管理路径 | 依据实际角色、操作和对象归类，不把后台可访问视为全部管理路径已测 |
| 9. 基础设施与生产发布路径 | 特权操作、生产发布及其支撑业务 | 对应实际控制和影响范围，共享控制证据不重复计权 |
| 10. 异常处理、资源滥用与恢复 | 相关业务的异常处置与恢复，以及适用的 D2、D5–D7 等检查 | 仅继承实际执行的场景；该项已测不能自动填满其他流程的异常维度 |

对应关系可多对多，以报告的功能、模块、范围说明和结论为依据。共享证据可支持多个已存在流程的检查，但每个流程的同一维度只计一次；不能因同一业务经过多个服务类别而新增计分流程或权重。确实需要拆分子范围时保留父项总权重。

七个 D 维度编号和目标直接沿用，无需测试方再提供另一套矩阵。评级侧能从明确的终审范围对应到流程时直接采用；只有十项摘要而无法确认具体流程、子范围或适用性时，受影响项标 U，不自行猜测完整覆盖，也不要求补交逐条用例。

## 3. 七个横向检查维度

| 编号 | 维度 | 测试目标与 Web3 场景 |
| --- | --- | --- |
| D1 | 攻击与滥用防护 | 验证认证、越权、输入篡改、步骤绕过及跨组件攻击；如替换授权对象、收款人或生产配置 |
| D2 | 错误处理与部分失败 | 超时、拒绝、部分成功等情况下不产生危险状态；如链上已成功但后台超时后引导重复执行，或失败后使用危险默认值 |
| D3 | 并发、重复与顺序控制 | 并发、重试、重放和乱序不产生额外执行或权益；如重复提现、Webhook 重放、并发领取 |
| D4 | 数据与状态一致性 | 用户意图、展示、签名、后台状态及链上结果正确关联；如切换钱包后沿用旧账户状态、失败却记为成功 |
| D5 | 冗余与故障切换 | 必要组件故障后，替代路径或停止方式符合业务要求；如备用 RPC 网络正确、备用报价语义一致 |
| D6 | 安全降级与资源耗尽 | 故障或资源不足时不绕过校验、不无界重试、不使攻击者轻易耗尽关键资源；如验签失败不能直接放行 |
| D7 | 恢复与可追溯性 | 重启、恢复、回滚后不重复执行、不恢复失效权限，关键操作可关联追踪；如恢复数据库后不重新接受已使用的 nonce |

上述是安全目标，不强制指定实现。没有备用服务可以通过安全停止满足适用要求；多节点、多供应商或自动切换本身不加分。正常业务可用性目标与资金、权限安全结合实际场景确定，不要求所有项目具备多活、零中断或统一恢复时长。

评级侧只继承报告实际完成的架构核验、受控故障、切换及恢复结论。授权、计划或文档声明不等于实际完成；不能仅凭常规外部扫描认定这些维度已覆盖，也不在评级阶段临时补做测试。

## 4. 范围、权重与关键验证项

### 4.1 流程权重

| 权重 | 具体条件 | 示例 |
| --- | --- | --- |
| 5：关键 | 可直接影响资产、授权、关键身份，或改变生产环境与资金执行 | 交易构造、资金签名、管理员操作、生产发布 |
| 3：重要 | 影响必要业务、重要数据或恢复能力，但不直接形成上述后果 | 非资金后台业务、必要查询、部分恢复入口 |
| 1：辅助 | 不影响资金、关键权限及必要业务 | 普通内容展示、辅助功能 |

按实际后果分配权重，不能机械按模板名称确定。例如直接决定交易执行的报价输入也可能属于权重 5。

范围和权重由评级侧在本次评分计算前，根据实际业务影响固定并记录依据；不要求在渗透规划或交付阶段形成评分权重，并遵守：

1. 评级分母覆盖项目实际存在的相关业务，不只包含本次购买的服务范围。尚未采购或未获授权的相关测试如实列为未覆盖。
2. 同一业务不能通过拆成大量简单流程稀释关键遗漏；共享组件的适用测试证据可以复用。
3. 业务或维度确实不适用才可排除，并记录理由。预算不足、项目方不提供条件或测试风险较高，不属于 N/A。
4. 范围、结构或权重变化应记录事实依据和版本，不按报告覆盖多少、Finding 等级或预期得分倒推调整；后续新增资料引起变更时保留前后对应。
5. 同一流程内的适用维度默认等权，不另设七套未经校准的维度权重。

流程或维度仅为描述覆盖而拆分时，保留父项总权重，在父项内部按业务影响和明确范围合理分配，不给每个子流程重新追加一整份 5／3／1 权重。保持合理粒度即可，不追求精确到接口数、用例数或代码行；实际新增业务另行调整顶层范围并注明原因。

### 4.2 关键验证项

评级侧根据实际业务和控制路径，在计算前固定少量关键验证项，作为 G 的判断依据。它们不构成追加给测试方的委托或交付要求：

| 关键验证项 | 适用条件 |
| --- | --- |
| 身份与操作权限绑定 | 身份或角色可以控制资产、敏感数据或生产配置 |
| 签名／交易与业务意图绑定 | 项目生成、请求或执行授权、签名和交易 |
| 关键管理与发布路径 | 相关入口可替换用户应用、交易配置或执行资金操作 |
| 资金操作的重复与部分失败处理 | 项目承担后台执行、回调、记账或其他跨系统资金状态管理 |

关键验证项绑定具体流程、组件和维度，不将所有权重 5 流程的七个维度自动全部标成关键。适用性根据业务事实判断，覆盖根据报告判断；没有对应组件或能力时说明不适用依据，业务或控制路径无法确认时保留未知，不因报告未提及而删除该项。

## 5. 覆盖状态与计算

### 5.1 矩阵格子的取值

| 状态 | 取值 | 判定与说明 |
| --- | --- | --- |
| 已完成测试，证据适用于当前系统 | 1 | 直接采信最终报告；如明确保留风险，另按第 6 节封顶 |
| 明确未覆盖，或当前版本已超出原测试范围 | 0 | 表示缺少适用测试保障，不等于已确认存在漏洞 |
| 部分覆盖 | 拆分后计算 | 按明确的已测／未测范围计算，不凭印象直接给半分 |
| 无法确认范围或当前适用性 | U | 待核验，不默认已测或未测 |
| 确认不适用 | N/A | 附理由后从对应分母排除 |

统一使用终审报告或已有交付清单归类范围与结果，各服务商同等采信，不要求按本标准重交矩阵、用例或测试记录。已测范围可以计入覆盖，但报告明确保留的风险仍限制最终得分。

报告原状态和评级取值分别保留，按以下规则转换：

| 报告披露 | 评级处理 |
| --- | --- |
| 已覆盖 | 对明确对应且证据仍适用的流程检查记 1；仍有漏洞时另由 R 处理 |
| 未覆盖 | 对实际适用且明确未测或未完成的范围记 0 |
| 不适用（未委托） | 根据项目实际业务判断；业务存在且明确未测的范围记 0，业务是否存在或对应范围不清则 U，不直接从分母排除 |
| 不适用（业务不涉及）或维度确实不适用 | 依据报告及业务事实确认后记 N/A，并保留理由；无法确认则 U |
| 不适用但未说明原因 | 先核对已有范围说明；仍不能区分未委托和业务不涉及时记 U |
| 已覆盖与未覆盖并存 | 按有依据的功能或子范围拆分；无法界定的剩余部分记 U，不固定取 0.5 |
| 空白、待填或执行情况无法确认 | 记 U，不推定为未测、通过或不适用 |

例如，报告“核心业务流程与业务规则／D3”仅明确存入已测、赎回未委托且未测，评级分别继承其范围；不能把整个核心业务视为已覆盖，也不能排除赎回。黑盒、灰盒、白盒只说明测试条件，不直接改变覆盖取值或增加分数。

上述转换先保留每份报告的事实，再合并所有仍适用的报告。某份报告未委托该项，不抵消另一份报告对相同范围的明确有效覆盖；重叠覆盖只计一次，全部适用材料均明确未测时才记 0。同一范围的结论存在尚未解决的冲突时保留原文并标明待核验，不择取有利结论；已确认保留风险仍按第 6 节处理。

### 5.2 覆盖公式

对流程 `i`：

- `wᵢ`：流程权重，为 5、3 或 1。
- `nᵢ`：该流程适用检查维度数。
- `vᵢⱼ`：维度 `j` 的覆盖取值。完整覆盖为 1，明确未覆盖为 0；有明确子范围时，由评级侧在该维度内部计算覆盖比例。

```text
流程覆盖率 cᵢ = Σⱼ vᵢⱼ ÷ nᵢ

业务流程覆盖分 C = 100 × Σᵢ(wᵢ × cᵢ) ÷ Σᵢwᵢ
```

完整格子不拆分时，等价于“已完成测试的适用维度数 ÷ 全部适用维度数”。需要拆分时，评级侧依据报告明确的实际子范围，在计算前固定子项、分配依据及分母；子项只在所属维度内归一化，不能通过增加简单子项扩大该维度权重。

不适用维度不计入 `nᵢ`。若整条流程没有适用内容，核对其是否确实不属于评级范围，说明后排除，不执行除零或自动记满分。

### 5.3 未知项

有 U 时，保持已声明范围和权重，分别将未知覆盖取 0 和 1，计算 C 的下界和上界，并展示未知范围。未知项不剔除后算满分，也不当成已确认测试失败。

关键范围或关键验证项无法确认时，暂不发布确定总分。若关键范围本身尚不完整，先补齐范围，不用不完整分母制造精确分数。

该限制只作用于受影响的流程、对象及其必要汇总，不使无关流程的已确认结论失效。已有范围无法完整获知时，先展示已确认范围、分项及缺口，不为评级追求穷尽所有业务；必要范围不完整时不把已知子集称为全项目覆盖率。

## 6. 封顶规则

### 6.1 关键遗漏封顶 G

```text
G = 100：适用的关键验证项均已覆盖
G = 59：至少一个适用的关键验证项明确未覆盖
```

59 分表示不能凭其他大量覆盖认定整体基本合格，不表示未测部分已确认存在漏洞。关键项未知时标待核验，不硬给确定总分。

### 6.2 报告保留风险封顶 R

仅继承最终交付报告中仍保留的风险等级，不重新判断技术严重性，不把整改与复测另设评分项。

Finding 的十项所属项目标识用于定位来源；评级侧结合实际影响流程和版本建立风险对应，不按该类别直接扣分。跨项目问题共用原 Finding ID，关联其他受影响流程，不重复累计。同一问题已接受或部分缓解但仍有风险时继承最终保留结论；只有修复声明而没有终审复核结论时，不自行解除风险。终审是否存在保留风险无法确认时，不因缺少问题表而推定 R=100。

报告中的中心化问题只作信息说明，不纳入 R，也不以其报告等级扣业务攻防分；该类风险只根据当前链上权限和控制信息评价。排除的是终审列明的中心化问题，不将非中心化类的认证、验签或权限实现漏洞一并排除。无需新增草稿或历史中间版本的状态合并机制，采用终审结论即可。

| 排除中心化问题后，终审仍保留的最高风险等级 | 分数上限 R |
| --- | ---: |
| Critical | 0 |
| High | 49 |
| Medium | 79 |
| Low | 94 |
| 无上述保留风险 | 100 |

风险等级在测试服务中采用统一定义。外部报告的等级无法直接对应时，披露原结论和待对应状态，不在评级阶段重新做技术裁决；未确定 R 前不发布确定最终分。

通用免责声明、历史已关闭问题、建议性改进不自动作为保留风险。多个问题取最严格上限，不按数量累减；同一风险在多个流程出现时共用标识。

## 7. 最终分与示例

范围、覆盖及风险状态可确定时：

```text
业务攻防评级分 S = min(C, G, R)
```

该分数表示基于仍适用的渗透测试及相关业务验证覆盖，现有证据能够支持的业务安全能力水平，不是安全概率，也不代表未来不会被攻击。

示例：三个流程权重分别为 5、3、1，覆盖率分别为 100%、2/3、0：

```text
C = 100 × (5×1 + 3×2/3 + 1×0) ÷ (5+3+1)
  ≈ 77.8
```

| 其他条件 | 最终分 |
| --- | ---: |
| 关键验证项均覆盖，无保留风险 | 77.8 |
| 至少一个关键验证项明确未覆盖，无更严格风险上限 | 59 |
| 其他条件相同，最终报告仍保留 High 风险 | 49 |

存在未知项时，分别展示覆盖区间、已确认封顶和缺口；不能直接把覆盖分区间上界当成最终确认分，也不能让未知项抵消已确认风险。

## 8. 证据适用性与更新

| 情况 | 处理 |
| --- | --- |
| 日期变旧但未发现适用前提变化 | 不仅因日期自动扣分；展示测试日期及当前适用性核验状态 |
| 前端、后台、发布流程或业务配置改变 | 按依赖关系识别受影响格子；不继续沿用已不适用结论，也不使无关覆盖全部失效 |
| 已确认新增或变更内容未测试 | 对应范围为明确未覆盖，必要时调整分母并记录版本 |
| 无法确认当前版本与报告关系 | 受影响范围标 U，不将未核验等同于安全或有漏洞 |
| 镜像或其他测试环境的报告用于生产评估 | 评级侧结合报告、环境说明和已有变更材料判断对应；已知差异限定受影响范围，不能确认的部分记 U，不自动认定生产已测，也不因采用镜像环境统一否定报告 |
| 客户确认敏感信息防护、最小授权或环境准备 | 作为测试条件和范围说明；不据此将相关安全检查记为已覆盖或直接加分 |
| 单纯链上状态变化 | 不自动使全部链下测试失效；仅当改变相关交互、业务规则或测试前提时联动 |
| 完成后续测试并形成最终结论 | 更新对应格子及报告引用；报告已消除的保留风险按新结论解除封顶，不另奖整改或复测分 |

不要求常驻渗透工具持续运行才能保留评级。后续定期或变更触发的测试形成新证据，评级按适用范围更新。

## 9. 完整报告、公开报告与评级的对应

报告固定终审事实，评级侧保存报告服务编号、检查和 Finding ID，并生成自己的流程及评估记录 ID，保留双向引用。报告不需要使用评级流程编号，也不要求包含权重、关键验证标记、C/G/R 或分数。

| 来源内容 | 评级侧用途 |
| --- | --- |
| 范围与授权确认、实际执行及差异 | 区分委托范围和实际业务，识别环境、角色、对象及未完成部分 |
| 十项服务 × D1–D7 矩阵及范围说明 | 按第 2.3 节映射到实际流程，按第 5 节形成覆盖值和未知项 |
| Finding 详情、终审汇总及复核结论 | 继承最终等级、类型、状态和影响范围，确定 R |
| 项目已有资料和版本变更说明 | 由评级侧补充实际业务范围、权重、关键项及当前适用性判断；不把项目声明当成测试结论 |

公开评级至少展示：

1. 评估业务范围、环境版本、测试日期和最新适用性确认时间；如引用当前链上事实，另列区块时间。
2. 流程及维度、权重和依据、关键验证标记、覆盖状态及缺口；保留原报告状态与转换原因。
3. 终审保留风险、C/G/R、最终分或区间及标准版本。
4. 来源报告和位置、范围映射及适用性更新记录。

上述评分信息由评级侧发布，不回写到渗透服务规范、客户填写表或原始报告。完整报告、脱敏版与评级通过稳定编号对应；公开材料保留关键限制和风险，敏感详情按权限保管，不因脱敏自动否定已确认的覆盖。

## 10. 外部公开标准的采用与取舍

| 来源 | 借鉴内容 | 不强制采用的内容 |
| --- | --- | --- |
| OWASP ASVS 5.0：V2 业务逻辑 | 流程顺序、业务限制、并发资源控制、操作一致性 | 不要求已上链交易像数据库事务一样回滚；测试失败识别、对账和适用补偿 |
| OWASP ASVS 5.0：V13 配置 | 超时、重试、连接限制、故障处理及必要外部依赖 | 不统一要求多活、HSM 或特定供应商产品 |
| OWASP ASVS 5.0：V16 日志与错误处理 | 安全失败、必要事件记录及敏感信息保护 | 不把采购 SIEM、建设全天候值守作为渗透通过条件 |
| ERC-4361：Sign-In with Ethereum | 适用钱包登录的域名、链、nonce 及会话绑定 | 不要求所有项目具有钱包登录，也不要求非 EVM 项目采用该协议 |

上述资料用于理解检查目标及报告范围归类，不直接产生本标准权重、分值、封顶或合规认证。具体测试按服务规范和授权执行，评级不以引用外部标准为由追加检查或交付要求。
