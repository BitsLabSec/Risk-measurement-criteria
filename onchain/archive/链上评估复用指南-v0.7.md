# BitsScore 链上评估复用指南

版本 v0.7｜2026-11-24。所有 DeFi 协议的链上评估包括**权限管理、参数配置、资金与外部依赖**。本指南规定执行顺序、项目汇总、封顶和交付。先用通用判据和各类型专项算出分项，再按本指南汇总。 [通用标准](./通用链上安全评估标准-v0.5.md) · [类型专项索引](../README.md)

## 1. 执行流程

### 1.1 第一步　固定评估范围、对象和快照

1. 以[前期准备](../../前期准备/assessment-preparation.md)的部署基线、全量关系图和业务模块为输入，沿用业务与控制记录 ID，列出本轮要判断的必要操作。DEX 可对应交易、结算和撤资，Lending 可对应借款、还款、清算和提款。同一链的本轮读数使用同一快照，跨链分别登记区块或检查点及其标识。
2. 沿必要操作，把图上的生产入口、共享权限凭证、全局配置、关键资金对象和直接依赖对应到实际地址或对象 ID。顶层对象足以判断时在该层停止。确需查看池或市场时，先说明哪个必要操作还无法判断、哪个指定对象能补齐证据，再登记该对象和选择理由。局部读数只支持对应的局部范围。
3. **每个项目每轮最多核验 50 个链上目标，跨链合计。** 合约、EOA、多签、时间锁和独立读取的 Sui 包、Cap、池或配置对象均计入。按「链 ID＋地址或对象 ID」去重，批量读取按其中的独立目标计数。范围清单为后续发现的控制实体和签名人预留额度。达到上限时停止扩大采集，记录剩余关键关系及受影响范围。

本步交付**范围清单**。记录纳入的产品和必要操作、生产版本、各链快照、核验的顶层对象及图节点、下钻对象及理由、目标数和剩余额度，以及排除范围和本轮未能取得的证据。

### 1.2 第二步　在原图上补齐实际控制关系

1. 保留准备阶段的特权角色节点，沿实际权限凭证、管理员配置或治理关系定位当前持有者。保留不同角色及其受控业务。多个角色确认为同一多签控制时，连接到同一个多签节点。
2. 在多签节点记录门限，在成员边记录已核对的签名地址或公钥及权重。不同多签共享同一个签名人时复用该签名人节点。从已有能力关系标明哪些角色须共同批准、哪些执行路径可以任选。对能够授予角色、替换控制者或通过升级、恢复和紧急入口达到同一后果的路径，继续追到实际控制端。
3. 把时间锁连接到它实际约束的执行路径。记录当前配置的强制等待时长、谁能改动这项配置、哪些路径可绕过等待。成员、门限、持有关系或延时证据不足时，标明未取得证据的关系及影响。核验目标仍受第一步的 50 个上限约束。

本步交付**补齐后的权限关系图**，沿用准备阶段的基线、角色及操作 ID。新增的地址、对象和关系保留快照与证据定位。从任一范围内关键操作，可以追到当前控制端、所需批准、有效延时及已知替代路径，或看到明确的证据缺口。

### 1.3 第三步　评估权限管理

以第二步补齐的图为输入，按用户权益和必要操作评价当前权限。各协议类型共用本节分表，表内数字为档位上限。按实际业务确定需要保护的资产、操作和有效退出路径。

1. **列清关键后果和范围。** H1 是任意处分用户资产或重写权益，H2 是受约束地改变存量用户的业务条件，H3 是在缺乏到期或独立恢复保障时阻断必要操作。区分影响全局、单个产品或局部对象。辅助角色按实际能力披露。
2. **找出每项后果的完整控制路径。** 直接路径和通过授予、升级、恢复及应急机制取得同等能力的路径都要列。必须共同批准的角色计算满足门限所需的最少不同密钥数，共用密钥只计一次。任选路径分别评价，同一后果取最弱路径。
3. **核实当前生效的权限配置。** 确认时间锁按机制公开约束操作内容，记录该控制路径的强制等待时长及最快可达的替代路径。涉及退出保护时，核对权限配置中是否保留相关退出入口，以及控制者能否在等待期内提前关闭该入口。延时档位按配置判定。

| 实际授权条件 | 无有效延时或不足 24 小时 | 有效延时达到 24 小时且不足 48 小时 | 有效延时至少 48 小时 |
| --- | ---: | ---: | ---: |
| 一把密钥可达，包括单签旁路 | 0 | 40 | 50 |
| 强制至少两把不同密钥共同批准，且没有单签旁路 | 80 | 85 | 95 |

在同一业务范围内，同一后果先取各路径的最低上限，业务权限档再取适用后果的最低上限。完整核验后确认无对应直接或间接危险能力时，该后果归 100 档。已确认必要操作永久受阻且无有效恢复路径时，该后果归 0 档。查不到多签门限、强制延时或替代保护的证据，按未具备相应保护计分。关键路径本身无法核实，导致必要权限检查无可用证据时，该检查记 0，在明细中注明缺证原因。 [结项规则](./通用链上安全评估标准-v0.5.md#5-证据缺失去重与结项)

#### 权限档内扣分

| 扣分项 | 扣分 | 触发证据及边界 |
| --- | ---: | --- |
| 共同授权关联 | 1 | 两个已预先识别的关键控制域共用实际控制端或签名密钥，须由成员、权重和实际路径证明。两条路径仍须至少两把不同密钥共同批准。沿用原关联修正，同一权限评分范围至多扣一次。若共享控制实际提供单签旁路，按单签重新定档。 |
| 关键角色已有授权或恢复备份退化 | 1 | 在 H1／H2 对应的资产处分、条件变更或 H3 对应的独立解限、恢复中，证实已部署的备用授权或待命恢复端失效，实际最弱授权、主恢复路径和相关必要操作仍全部符合本档。用链上角色状态及阈值或恢复路径证明。单凭没配置备份、地址相同或签名人近期未签名不足以扣分。 |
| 权限配置停用次要退出入口 | 2 | 现行权限配置使一条原已部署的次要退出入口失效，必要退出入口仍受原配置保护，强制等待及授权档位仍成立。若同一控制者已可关停必要退出入口或绕过延时，按现行配置重新定档。 |

| 档位上限 | 档内整数范围 | 适用扣分项 |
| ---: | ---: | --- |
| 100 | 96–100 | 适用已部署的关键安全恢复备份退化，且无对应危险能力的结论仍成立。 |
| 95 | 86–95 | 共同授权关联、授权或恢复备份退化、权限配置停用次要退出入口。 |
| 85 | 81–85 | 同 95 档，按本档的生效权限配置核验。 |
| 80 | 51–80 | 共同授权关联、授权或恢复备份退化。 |
| 50 | 41–50 | 授权或恢复备份退化、权限配置停用次要退出入口。 |
| 40 | 1–40 | 同 50 档，按本档的生效权限配置核验。 |
| 0 | 0 | 保留已证实的路径和后果。 |

仅对维持本档且有证据的独立问题扣分，使用通用档内公式和去重要求。例如最低档位上限为 85，同范围有已核实的共同授权关联，其他条件通过，最终记 84。 [通用档内公式](./通用链上安全评估标准-v0.5.md#13-先定档再计算档内分) · [既有关联规则](./lending-onchain-security-rating-standard-v0.15.md#621-跨关键控制域的关联修正)

本步交付**权限评分结果及路径明细**。按业务记录后果、影响范围、最弱路径、最少密钥数、有效延时、档位上限、适用下限、逐条扣分及最终分。用第二步的图节点及证据 ID 定位评分依据。

### 1.4 参数配置

1. 从第一步的必要操作出发，按业务功能选择专项。把关键对象绑定、参数组合、必要操作状态分别列入检查。每项记录要保护的权益、读取对象、消费路径及适用的硬约束或警戒依据。
2. 用相同快照或已记录的单次输入对照代码，确认当前生效值、单位、优先级和影响范围。共享配置读取一次。顶层证据不足时，按第一步的范围和额度核验已选局部对象。
3. 按专项判据先定 100／60／0 档，再按具体扣分项细评。已确认不适用的检查记 N/A。没有适用安全阈值的商业数值按披露处理。同一范围按通用公式或专项采用的组内公式计算。共享配置或局部异常按证据能够支持的实际范围呈现。

交付**参数配置结果及明细**。记录生效值、业务路径、判定依据、分档、受影响范围及证据缺口。 [配置通用判据](./通用链上安全评估标准-v0.5.md#3-参数配置)

### 1.5 资金与外部依赖

1. 对同一批必要操作和用户权益，使用对应专项找出资金承诺、到期条件、资金所在和实际付款路径。分别核实直接现金、资金能否调至目标以及何时可用。保留币种或份额单位。
2. 从业务消费端确定投入的有效输入及执行、结算和退出各自依赖的组件。核验实际生效的备用及承接范围。采用专项声明的停供情景时，当前状态与情景分别记录，沿实际业务边界检查可执行的替代。
3. 依据专项核对供付匹配及业务是否受限，先定档，再对独立问题细评。权限、配置和外部故障可以共用证据。同一根因在同一范围造成同一后果时，由责任项计一次。各自成立的独立原因按各自条款判断。必要条件缺证时按结项规则计分并留明细。 [结项规则](./通用链上安全评估标准-v0.5.md#5-证据缺失去重与结项)

交付**资金与外部依赖结果及明细**。逐必要操作列义务、可用资金、缺口或未核实内容、外部输入和替代、当前及适用情景结论、分档和证据定位。 [资金与外部依赖通用判据](./通用链上安全评估标准-v0.5.md#4-资金与外部依赖)

### 1.6 共用记录要求

- 定义每项要回答的风险问题，记录触发条件、实际路径、业务后果、已有保护和影响范围。区分当前异常、已证实的机制限制和假设压力。评分前固定适用规则、阈值、分母及权重。尚未校准的压力参数标为试评政策。
- 记录每项是必采还是选配，之后用于评分、披露还是引用。优先复用仍适用的快照、代码映射和汇总数据，按第一步的下钻条件决定新增对象。
- 保存读取对象、原值、单位、证据、失败及受影响范围。派生值保留计算公式和输入。机制稳定后按已确认的规则复算，部署、字段或业务逻辑变化时重新核对相应机制。

## 2. 共用采集清单

| 采集组 | 最少记录什么 | 来源与用途 |
| --- | --- | --- |
| 范围和锚点 | 链 ID、部署／市场／池 ID、代币类型及 decimals、区块或检查点号及哈希、链上时间／采集时间、包或实现版本、规则版本、核验目标数和范围缺口 | 同链同轮使用同一锚点。部署、源码版本与读取对象对应。跨链单列锚点，合计核验目标。 |
| 权限与控制 | 特权操作及影响范围、角色及凭证、实际控制端、成员、门限及权重、共同签名人、所需批准、授予／升级／恢复路径、有效延时及证据缺口 | 将链上的 owner、Cap、治理或多签状态接到已确认的代码关系图，为后续权限评估提供路径依据。 |
| 业务风控配置 | 对象、单位与用途绑定；实际生效的费率、额度、风险参数与覆盖模式；暂停／冻结／替代状态 | ABI／源码说明单位和真实比较条件，链上读当前值。区分禁新增、存量限额、必要操作受阻。只采该类型实际使用的字段。 |
| 资金状态 | 按池与币种保存供应债权、借款、直接现金、费金库实际余额、账面国库份额和管理资产；衍生表保留价格时效与估值 | 链上池／储备／金库／已知管理器。原币优先；`现金`、`债权`、`借出`、`留存资产`分开。不同池或币不能默认互抵；同一金额不同时计作用户流动性和损失储备。无同类资产负债模型时换对应业务字段。 |
| 关键依赖 | 必要业务入口、实际报价或组件、主／备绑定及启用、最终消费端校验、异常和回退路径、受影响操作／范围 | 链上状态＋消费路径。分别核验过期、异常返回、调用失败或暂停；共同依赖和同源主备不能重复计冗余。缓存过期与实际无法更新分别记录。 |
| 收入和历史（按需披露） | 协议归属利息、窗口、来源范围、币种或估值基准；若已有可核验数据，再区分应计、到账、留存和用途 | 既有协议／索引汇总可作代理或交叉核对。混合手续费、当期 APR、借款本金、账面利息不能替代实收；不要求为披露项新增逐笔采集。 |

统一字段至少包括 `item_id / scope_id / required_or_optional / score_or_disclosure_or_reference / status / raw_value / unit / anchor_or_window / evidence_refs / formula_or_rule_id / weight / score_or_null / reason / impact_scope`。有档位的计分单元另存上限、下限、定档事实 ID、各扣分事实 ID、规则及分值、合计及档内得分。缺证导致的 0 分记录为数值 0，并区分原因「证据未取得」与「已证实失败」。`N/A` 表示已确认不适用。另区分未启用、范围外和引用项。

## 3. 项目汇总与正式交付

| 大项 | 统一权重 | 主要回答 |
| --- | ---: | --- |
| 权限管理 | 30% | 谁能取得危险能力，哪些约束真能阻止越权或让用户退出。 |
| 参数配置 | 30% | 当前生效配置是否满足安全约束，能否支持必要操作。 |
| 资金与外部依赖 | 40% | 资金能否按期履约，必要输入和组件当前是否可用。 |

直接使用前期按功能划分的业务模块。合约、池及版本作为模块内依据。按以下顺序汇总。

1. **算各业务的分项原分。** 每个业务在各大项下给一个适用的原分。专项明确采用组内公式时先算组内结果，否则按通用定档和档内扣分规则。缺证的 0 分进分母，已证实 N/A 或仅引用其他责任项的结果不进分母。
2. **算业务原分和最终分。** 按 30／30／40 对该业务独立适用的大项加权，用适用权重之和作分母。局部风险按本节封顶表给该业务上限。封顶只对受到影响的业务生效。
3. **算项目原始分及最终分。** 业务封顶压低原分时，该业务用于汇总的各大项分，按「业务最终分 ÷ 业务原分」同比折减。业务原分为 0 时直接用原分。原定档和分项原分保留，折减值只用于项目汇总。每个项目大项内对适用业务分等权平均，再按固定的 30%／30%／40% 加权得到项目原始分。只有覆盖全项目的条件才应用项目级封顶。同一风险按实际范围应用一次封顶，已用于项目级封顶的条件不再给业务施加一次同因封顶。

例如三个业务的适用分分别为 100、70、100 时，该大项得 90。三个业务原分都是 100，其中一个因局部风险封到 60，其他两个照常计入，项目原始分为 86.67。整个项目大项确无独立适用模块时，交付已评分项并标「总分不适用」；有确证触发项目级 0 分封顶时直接交付 0 分。计算保留中间精度，统一展示至两位小数。 [现行汇总规则 JSON](./project-onchain-rollup-v2.json)

### 项目和业务风险封顶

影响范围按实际控制路径、受影响资产和必要操作认定。先判 0 和 60 的风险条件；未触发时，取已证实满足的最高保护档。**最终分取该范围原始分和适用上限中的较低值，发布分 60 及以下为不及格。**有确证触发 0 分封顶时，该范围直接交付 0 分。

| 上限 | 适用条件 |
| ---: | --- |
| **0** | 有确证表明可以在短时间内以极低成本影响该评分范围的全部资产，或明显的部署错误使该范围的核心业务无法正常运行。例子包括单个 EOA 可直接处分该范围全部资产，或关键估值直接使用可低成本显著改变的单一交易对储备比例并会牵连全部资产。 |
| **60** | 有确证表明可在短时间内以低成本影响部分资产或功能，且核心业务仍能正常运行，例如单个 EOA 可支配协议手续费收入，或实际生效的危险参数范围允许造成局部损失。亦用于必须有保护的控制或必要参数未能证明具备 80 档条件的范围，按缺证原因记录。 |
| **80** | 影响该范围的关键授权均要求有效多签，无法通过单签达到同一后果，必要参数设置合理或由代码作合理的固定约束。 |
| **85／95** | 在 80 的基础上，按第 1.3 节核验同一路径的时间锁和相关退出保护配置。关键路径的最短有效延时达到 24 小时但不足 48 小时，上限 85。至少 48 小时，上限 95。 |
| **100** | 在 95 的基础上，仍有覆盖关键路径的独立强制批准或无法由该控制者移除的硬约束，对同一风险提供额外保护。已核实该范围没有特权角色，也没有可调参数时，上限为 100。必要资金与依赖等检查均通过时，这类完全去中心化业务得 100 分。多个独立业务组成的项目，已确认项目层不存在影响全局的权限、可调参数或符合封顶条件的风险时，项目层上限为 100，各业务仍各自封顶。 |

短时间按权限配置和机制允许的最早生效条件判断。低成本依据实际所需权限、前置条件及成本相对受影响价值的量级判断。评分表写明风险能影响什么、最快生效条件、成本依据和受影响范围。单个 EOA 地址或某种价格输入的名称只是线索。按重大风险触发 0 或 60 档时必须有实际能力或故障后果的证据；必要安全保护缺证导致的 60 上限另记原因。

## 4. 复合项目怎样选专项

按业务实际承担的用户权益和必要操作选专项。路由调用池时分别记录路由的条件保障和底层池的资金责任。共享配置或依赖按其实际影响范围引用。每个业务使用本类型的输入和判据，项目结果按第 3 节汇总。缺少适用专项或必要证据时，保留已核实的范围和结论。 [类型专项索引](../README.md)
