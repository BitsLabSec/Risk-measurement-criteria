# BitsScore 链上安全评估标准

- 版本 v1.1，2026-11-25
- 依据：[评分骨架 v1.1](../评分骨架.md) 第 3 节。本文与骨架冲突时，以骨架为准。
- 本文是链上评估**唯一的通用规则**。各类型专项只补充「读哪些对象、用什么公式、硬约束和警戒阈值是什么」，不另立档位、扣分或汇总规则。 [专项索引](./README.md) · [专项模板](./专项模板.md)
- 历史规则（通用标准 v0.5、复用指南 v0.7、共同规则、汇总 JSON v1/v2）见 [archive](./archive/)，只用于复算旧结果。

## 1. 回答的问题

按快照时点的实际链上状态，协议的**权限、参数、资金和依赖**能否支持用户完成必要操作，例如交易、还款、提款、清算、赎回。

链上评估不重新找代码漏洞。代码能做什么，以前期准备和代码安全的结论为准；链上评估只看**现在**谁在控制、参数是多少、钱在不在、依赖能不能用。

## 2. 执行流程

本节是规则层面的流程。agent 逐步执行时，按[工作流](../工作流/README.md)的 O1–O8 步骤卡填写，计分由脚本完成。

### 第 1 步　固定范围和快照

1. 从[前期准备](../前期准备/assessment-preparation.md)取得部署基线、业务模块、特权角色和关键控制。业务模块直接沿用前期准备的划分。
2. 为每个业务列出**必要操作**，即用户为了保住自己的权益必须能完成的操作。例如：
   - Lending：还款、提款、清算
   - DEX：交易、撤资、领取手续费
3. 每条链固定一个快照（区块号或检查点、哈希、时间）。同一条链上的所有读数都使用这个快照。
4. **取证预算**：每个项目每轮最多核验 **30 + 15 × 业务数** 个链上目标（各链合计）。合约、EOA、多签、时间锁，以及单独读取的包、Cap、池或配置对象，各算一个目标，按「链 ID + 地址或对象 ID」去重。
   - 预算的目的是防止无限制地翻查交易和无关地址。只读取专项检查表和权限追踪需要的对象；读清单之外的对象，必须写明它服务于哪个检查项。
   - 预算优先用于必需检查：先读顶层的共享对象（全局配置、权限凭证、主储备）；需要逐池或逐市场读取时，先写明是哪个必需检查要用它。
   - 必需检查读完后还有预算，才读可选项和披露项。
5. **只用单次快照能读到的数据计分**（[骨架第 3.3 节](../评分骨架.md)）。不扫描历史交易或事件，不枚举全部用户或仓位。协议没有存储某个检查项需要的聚合值时，该检查项只披露、不计分，并写明原因。

交付物：**范围清单**，包括业务、必要操作、快照、已核验的目标及数量、未纳入的范围。

### 第 2 步　补齐权限关系图

在前期准备的关系图上，从每个特权角色追到**当前实际控制者**：

- 多签：记录门限、成员地址和权重。多个角色由同一个多签控制时，连到同一个节点；不同多签共用同一个签名人时，复用这个签名人节点。
- 时间锁：记录它约束了哪些路径、当前的最短等待时间、谁能修改这个等待时间、有没有能绕过它的路径。
- 继续追授予、升级、恢复和紧急入口，直到找出所有能达到同样后果的路径。

交付物：**权限关系图**。从任何一项关键操作出发，都能看到当前控制者、需要几把密钥、实际延时多久，以及有哪些替代路径。

### 第 3–5 步　评三个大项

按第 3、4、5 节，逐个业务给权限管理、参数配置、资金与外部依赖打分。

### 第 6 步　致命项和汇总

按第 7 节检查致命项，再按第 8 节算业务分和项目分。

## 3. 权限管理

### 3.1 三类后果

对每个业务，分别检查三类后果：

| 编号 | 后果 | 例子 |
| --- | --- | --- |
| H1 | 任意处分用户资产，或重写用户权益 | 转走池内资产；升级合约后替换记账逻辑；直接修改用户余额或债务 |
| H2 | 在约束范围内改变存量用户的条件 | 调整清算线、费率或抵押率，且调整会作用到已有仓位 |
| H3 | 无限期阻断必要操作 | 暂停还款、提款或撤资，并且没有自动到期，也没有独立的恢复路径 |

能力是否存在，以前期准备的代码梳理为准。只能阻止「新增业务」的开关（如暂停开新仓），不算 H3。

### 3.2 找最弱路径

1. 对每类后果，列出所有能达到该后果的完整路径：直接调用，以及通过授予角色、升级合约、恢复或紧急入口拿到同等能力的路径。
2. 每条路径都要计算两件事：
   - **最少密钥数**：要满足这条路径上所有必需的批准，最少需要几个不同的签名地址。
     - 同一个地址出现在多个多签里，只算一次。例：路径需要多签 A（2/3：a、b、c）和多签 B（2/3：b、c、d）都批准，b、c 两个地址签名就同时满足两者，最少密钥数是 2。
     - 多签的成员本身是多签时，递归展开到最终的签名地址。
     - 按权重计算的多签，取能凑够门限的最少地址数。
     - 不按门限占成员数的比例降档。门限和成员数只做披露。
   - **有效延时**：这条路径上不可绕过的强制等待时间。下列情况延时按 0 计：
     - 等待内容不公开；
     - 存在能跳过等待的路径；
     - 在等待期间，控制者能先关掉用户的退出入口。
3. 每类后果按下表给分，取所有路径中**分数最低**的那条：

| 最弱路径需要的授权 | 延时 < 24h | 24h ≤ 延时 < 48h | 延时 ≥ 48h |
| --- | ---: | ---: | ---: |
| 一把密钥即可（包括 EOA、1-of-N 多签，以及任何单签旁路） | 0 | 40 | 50 |
| 至少两把不同的密钥 | 80 | 85 | 95 |
| 完整核验后，确认不存在达到该后果的能力 | 100 | 100 | 100 |

4. **权限大项分 = H1、H2、H3 三项中的最低分。** 不设档内扣分。

补充规则：

- 查不到门限或延时的证据时，按「没有」处理，例如按单签计、按延时为 0 计。
- 角色暂时没有持有人，或者只是没找到路径，都不能直接判定为「不存在能力」。要给 100 分，必须完成第 2 步的全部追踪。
- 权限配置已经让必要操作永久失效、而且没有任何恢复路径时，H3 记 0。
- **H3 按「谁能让阻断持续」评分。** 某个角色能暂停，但另一个角色能解除暂停、并能撤销前者的权限时，阻断能否持续取决于后者。这时这条 H3 路径的最少密钥数和有效延时，取「能阻止恢复的一方」的条件。例：守护者 EOA 能暂停提款，3/5 多签能解除暂停并撤掉守护者，H3 按 3/5 多签计 80 分。暂停会自动到期、且不能连续续期的，不构成 H3。
- **升级**：只要能升级合约，就算 H1，不区分升级策略。只有确认不能再升级时（例如 Sui 的 UpgradeCap 已销毁、EVM 合约不是代理或代理管理员已放弃权限），才算不存在这种能力。
- **出金限速**：一条 H1 路径如果受代码强制的出金限速约束（例如每 24 小时最多转出 TVL 的一定比例），这条路径按 H2 计。限速必须由合约代码强制执行，而且不能被同一个控制者关掉或调大；能被关掉或调大的，不算限速。

## 4. 参数配置

### 4.1 检查项

| 编号 | 检查项 | 怎么查 |
| --- | --- | --- |
| C1 | 关键对象绑定 | 资产、池或市场、收款方、价格源、策略、结算组件是否绑定正确，单位和精度是否一致。 |
| C2 | 参数及组合 | 当前生效的费率、限额、风险参数，按代码中实际的使用方式联合计算，检查是否违反硬约束、是否触发警戒阈值。 |
| C3 | 必要操作状态 | 暂停、冻结、白名单、限额等开关，对必要操作的实际作用。 |

具体要读哪些字段、用哪些公式、硬约束和阈值是什么，以对应专项为准。

读数要追到代码的使用位置，确认单位、优先级（全局默认值与局部覆盖值）和作用范围。共享配置只读一次。

### 4.2 分档

| 得分 | 条件 |
| ---: | --- |
| 100 | 通过：当前值满足专项列出的硬约束，必要操作能完成。 |
| 90 | 通过但有弱化：必要操作仍能完整、按期完成，但已证实某个已部署的次要保护、备用路径或便捷入口失效。不论有几个这类问题，都记 90，不累计。 |
| 60 | 部分受限：触发专项列出的警戒阈值；或者必要操作部分受阻，但同一范围内仍有可用路径。 |
| 0 | 失败：违反专项列出的硬约束；或者必要操作完全受阻，且没有替代路径。 |
| N/A | 已确认该机制不存在，并附依据。 |

判定顺序：先查 0 档条件，再查 60，然后查 90，最后才是 100。

**参数配置大项分 = 该业务下各适用检查项得分中的最低分。** 业务内有多个市场或池子时，按第 8 节的「多市场业务」规则计算。

- 专项没有列出阈值的数值（例如费率高低、利用率、TVL）只披露，不计分。
- 「停止新增、允许存量退出」属于正常的风控操作，不算受阻。
- 机制本身规定的等待（例如解锁期）也不算受阻。

### 4.3 主流资产的口径

专项中凡是提到「主流资产」或「非主流资产」，一律按以下口径判断。满足任一条即为主流资产：

1. 该链的原生代币（例如 SUI、ETH）；
2. [CoinGecko](https://www.coingecko.com/) 市值排名前 20 的资产；
3. [DefiLlama 稳定币榜](https://defillama.com/stablecoins) 市值前 5 的稳定币。

第 2、3 条在本链上必须是发行方原生发行的版本，或该链官方文档列出的规范桥接版本；其他包装或桥接版本不算。排名在评估当天查询，记录查询日期和截图或链接。

## 5. 资金与外部依赖

### 5.1 检查项

| 编号 | 检查项 | 怎么查 |
| --- | --- | --- |
| F1 | 资金义务与可用资产 | 先确定欠用户什么（币种、数量或份额、期限、资格条件），再核对同币种的可用资金。 |
| F2 | 资金调回 | 从付款或退出入口，追到资金实际在哪里、能调回多少、需要多久、有什么限制。 |
| D1 | 必要输入 | 必要操作实际使用的报价、价格、签名、兑换率等输入当前是否有效。 |
| D2 | 依赖路径与替代 | 执行、结算和退出各自依赖的外部组件当前是否可用；有备用的，检查备用能否真正接上。资金存放在其他协议中时，按下面的「依赖协议的评分」处理。 |

对账规则：

- 按**同池、同币种**配对。不同池、不同币种的资金，不能默认互相抵用。
- 直接现金、应收债权、外部策略里的资产分开记录。只有证实能按期调回的资金，才计入可用资金。
- 同一笔资金只能用于覆盖一项义务。
- 用区间核对时：可用资金的下界不低于义务的上界，才算覆盖；义务的下界高于可用资金的上界，算有缺口；两个区间重叠时，按「部分受限」处理，并披露区间。
- TVL、收入、利用率等只披露，除非专项为它们列出了阈值。

### 5.2 分档

与第 4.2 节使用同样的 100／90／60／0／N/A 五个结果，含义换成资金和依赖：

| 得分 | 条件 |
| ---: | --- |
| 100 | 义务有足额的可用资金，必要输入和路径都有效。 |
| 90 | 同上，但已证实某个备用来源、备用路径或便捷入口失效，主路径仍能完整承接。 |
| 60 | 触发专项列出的警戒阈值；或者必要操作部分受阻，但仍有可用路径。 |
| 0 | 违反硬性兑付约束；或者必要输入或路径失效，导致必要操作完全受阻且没有替代。 |
| N/A | 已确认不存在这项义务或依赖。 |

**依赖协议的评分。** 业务把资金存放在其他协议中（例如金库把钱存进某个借贷协议）时：
- 被依赖的协议有 BitsScore 链上评分、而且低于 60 分，这一项触发警戒，记 60；
- 被依赖的协议没有评分，只做披露。

**资金与外部依赖大项分 = 各适用检查项得分中的最低分。** 业务内有多个市场或池子时，按第 8 节的「多市场业务」规则计算。

当前状态和假设情景（例如「如果唯一报价源停止」）要分开记录。只有专项明确把某个情景列为计分项时，该情景才计分；否则只披露。

### 5.3 通用预言机检查（OR）

适用于所有用价格估值的业务，例如借贷、杠杆、永续、CDP。各专项的 D1 直接引用这些编号，不重复定义。

- 每个关键估值价格源检查一次；共用的价格源只查一次，计入每个用到它的市场。
- 读的是代码实际使用的读价函数和参数。参数存在配置对象里的，读快照值；写死在代码里的，以前期准备已核验的源码为准，并写出代码位置。

| 编号 | 读什么 | 警戒（触发记 60） |
| --- | --- | --- |
| OR-1 | 读价调用的函数和时效参数 | 没有任何时效上限。例如用 Pyth 的 `get_price_unsafe`／`getPriceUnsafe`，或者把最大价格年龄设为不限 |
| OR-2 | 允许的最大价格年龄；推送型价格源的心跳 | 拉取型（Pyth、Switchboard 等由使用方按需更新）：最大年龄 > 300 秒。推送型（Chainlink 等由预言机定时推送）：最大年龄 > 心跳 × 2。OR-1 已触发的，本项不再单独检查 |
| OR-3 | 是否检查置信区间（只适用于提供置信区间的价格源） | 只披露，不计分 |
| OR-4 | 是否检查 L2 排序器的在线状态（只适用于 Arbitrum、Optimism、Base 等 EVM L2） | 没有检查。不在 L2 上的记 N/A |

依据：[Pyth 最佳实践](https://docs.pyth.network/price-feeds/best-practices) · [Sui 预言机安全指南](https://docs.sui.io/onchain-finance/oracles/oracle-safety) · [Chainlink 预言机安全要点](https://dev.to/0xsaff/chainlink-oracle-security-considerations-4o2c)

## 6. 归属和去重

一个事实只在一个大项计分，其他大项只引用。

| 情况 | 在哪里计分 | 其他大项的处理 |
| --- | --- | --- |
| 某人**能**修改参数或替换依赖 | 权限 | 配置和依赖只看当前值，不因为「能改」而扣分 |
| 参数或绑定**当前值**错误 | 配置 | 依赖引用这一事实 |
| 绑定正确，但外部输入或组件当前失效 | 资金与依赖 | 配置引用这一事实 |
| 资金不足 | 资金与依赖 | — |
| 同一个根因影响多个业务 | 在每个受影响的业务里，分别按该业务受到的后果判断 | — |

被引用的事实不进入引用方的最低分计算。某个大项如果只有引用、没有自己的检查项，结果标为「参见 X」，不计入业务分。

## 7. 致命项

某个业务**已确证**存在下列任一事实时，该业务分直接记 0。三个大项的分数照常展示。

| 编号 | 致命事实 | 需要的证据 |
| --- | --- | --- |
| X1 | 一把密钥在 24 小时内就能处分该业务全部用户资产（H1 覆盖全部资产） | 完整控制路径、当前持有人、门限、延时配置 |
| X2 | 关键估值输入可以被低成本操纵，并能影响该业务全部资产 | 估值输入的实际使用路径；操纵所需资金，并与可获利金额或受影响资产对比 |
| X3 | 部署或配置错误，导致全部用户的核心必要操作完全失效，且没有恢复路径 | 失效的入口、读数或交易证据，以及恢复路径的核查记录 |

- 只认已证实的事实。缺证、「可能」或推断都不触发致命项。
- 只对受影响的业务记 0。共享的控制（例如全局升级权限）影响到几个业务，这几个业务都记 0。

## 8. 汇总

```text
业务分     = 0.4 × 权限 + 0.3 × 配置 + 0.3 × 资金依赖
             （某个大项为 N/A 或只有引用时，从权重里去掉，剩下的权重重新归一）
业务最终分 = 触发致命项时为 0，否则等于业务分
业务权重   = max(该业务 TVL ÷ 项目总 TVL, 5%)，然后所有业务的权重再归一
项目链上分 = Σ(业务最终分 × 业务权重)
```

- TVL 取快照时点该业务托管的用户资产，以美元计。口径可以是 DefiLlama、官方 dapp 的统计，或链上模块余额乘以价格；同一次评估的所有业务用同一种口径，并记录来源和时间。纯路由等不托管资产的业务，取 5% 的下限权重。
- **多市场业务。** 业务内有多个市场或池子时（例如 Lending 的多个资产市场、DEX 的多个池子），配置和资金两个大项这样算：
  1. 对每个市场或池子，取它适用的全部检查项的最低分。全局配置、共用预言机等共享检查项，计入每个市场。
  2. 按各市场或池子的 TVL 加权平均，得到业务的大项分。不设下限权重。
  3. 得 0 分的市场或池子，在结果中单独列出。

  权限仍按整个业务评一次。
- 拿不到 TVL 时，所有业务等权，并在结果中注明。
- 项目层面的三个大项分只用于展示，同样按业务权重加权平均。
- 计算过程保留全部精度，结果展示到两位小数。60 分及以下为不及格。
- 机器可读的规则见 [project-onchain-rollup-v3.json](./project-onchain-rollup-v3.json)。

例：项目有两个业务。

- 主借贷：TVL 9000 万美元，权限 80、配置 100、资金 90，业务分 = 32 + 30 + 27 = **89**。
- 奖励池：TVL 100 万美元，权限 0、配置 100、资金 100，业务分为 **60**。

权重计算：借贷 98.9%，奖励池 1.1%，奖励池按下限提到 5%；归一后借贷为 0.989 ÷ 1.039 ≈ 0.952，奖励池为 0.05 ÷ 1.039 ≈ 0.048。
项目链上分 ≈ 89 × 0.952 + 60 × 0.048 ≈ **87.60**。

## 9. 证据不足

| 情况 | 处理 |
| --- | --- |
| 链上**公开**的必需事实没读到，例如参数值、余额、门限、延时 | 不出分。该检查记为「评估未完成」，同时列出缺什么、为什么没读到。存在未完成检查的业务和项目，不发布分数。 |
| 只有项目方能提供的证据查不到，例如链下储备承诺 | 按「没有这项保护」计分。 |
| 取证预算用完时，必需检查还没做完 | 同第一行，记「评估未完成」。 |
| 可选项或披露项没读到 | 只记录缺口，不影响分数。 |
| 参数没有查询函数，但存在合约状态里 | 直接读存储：Sui 读对象字段或动态字段；EVM 按已核验源码的存储布局计算槽位后读取。这属于快照读取，照常计分；要写明槽位和布局依据。 |
| 节点不支持按快照读取 | 在快照前后各读一次，结果一致即可使用，并注明「前后夹读」；不一致时换支持历史状态的节点，仍不行按第一行处理。 |
| Sui 原生多签的成员和门限 | 这些信息不在链上状态里。允许定向读取该地址发出的**一笔**交易（通常是最近一笔），从签名中解出公钥、权重和门限；计入取证预算。该地址从未发出交易、解不出来的，按第 3.2 节「查不到门限按单签计」。 |
| 市场或池子清单链上无法枚举（例如 key 只出现在事件里） | 从官方文档或前端取清单作为 key，参数和余额仍在快照上读取。结果中披露「市场清单取自官方列表，可能不完整」。 |
| 读出的值单位或含义无法从已核验源码确认 | 不猜。登记阻断缺口，按第一行处理。 |
| 协议没有存储检查项需要的聚合值，只能扫历史或枚举用户才能得到 | 该检查项只披露、不计分，写明原因。不算「评估未完成」。 |
| 读取失败（RPC 报错等） | 重试，或换一个数据源。仍然失败时，按第一行处理。 |

## 10. 每个结果必须带的字段

每个检查结果都必须能追溯到以下六样东西，缺一样就不算完成：

1. 快照（链、区块号或检查点号、UTC 时间）。最终交付物必须列出每条链的快照；
2. 读取的地址或对象 ID 及字段；
3. 原始读数及单位；
4. 适用的规则：本文条款加专项条款（例如 `onchain-v1.1 §4.2` 加 `lending-v1.2 L-C2.1`）；
5. 结果（100／90／60／0／N/A／只披露／评估未完成／引用）和定档理由；
6. 证据：交易、浏览器链接、代码位置。

具体的字段名和 JSON 结构只在一处定义：[交付格式](../工作流/交付格式.md)（检查项节点及其下的读数叶子）。本文和 [project-onchain-rollup-v3.json](./project-onchain-rollup-v3.json) 不再另写一份。

**有效期。** 分数只代表快照时点的状态。发生以下任一情况，结果视为过期，需要重评：权限持有人或门限变更、合约升级、核心参数改动。
